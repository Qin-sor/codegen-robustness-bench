## 1. 动机

主设计的「规格生成」任务里，模型的输入只有函数签名、依赖声明与功能规格；L2（结构）与 L3（语义）变换都发生在函数体内，模型看不到，所以 L2 / L3 的模型输入与 L1 逐字相同，这两级只对评测侧的项目副本有意义，对模型没有区分度（修复阶段的 open_issues 已指出）。

缺陷修复任务让模型直接阅读混淆后的目标函数：在每一级副本的目标函数里注入一个能被项目测试捕获的缺陷，让模型返回修正后的函数。这样三类混淆都作用在模型读到的代码上：L0 保留项目原有的名字，模型可能凭对项目的了解判断函数该做什么，L1 去掉名字线索，L2 / L3 进一步改变控制流与表达式的表面形态。两类任务并列报告，就能分别回答「生成是否依赖记忆」和「阅读理解是否依赖表面形态」。
注意：修复题的提示词里本来就是只差一处的原函数，候选没大改时相似度天然接近 1，单点缺陷的任何正确修复都逐字等于原函数（`restored` 约等于通过），所以修复任务里的 `similarity` 与 `restored` **不是**凭记忆还原的指标，要看级别之间通过率的变化（第 12 节 #26）。

## 2. 任务定义

- 输入：与生成任务相同格式的依赖上下文（includes / 类型 / 宏 / 全局 / 被调函数原型），**按注入缺陷后的函数裁剪**（被删掉 / 换掉的代码才用得到的原型、宏、全局不进提示词，第 12 节 #20），加上**该级副本里注入缺陷后的目标函数完整定义**（已去注释）。不给功能规格，不给测试输出，不说明缺陷位置。
- 要求：返回修正后的完整函数定义，签名不变，不新增 `#include`。
- 判定：与生成任务完全相同的 `evaluate`（替换 → 语法检查 → 构建 → 项目测试 → 归因）。通过 = 项目测试全过。

## 3. 变异算子（在 Lk 副本的目标函数体上做，AST 引导，复用 `bench/obfuscate/_edits.py` 的按偏移改写机制）

| 编号 | 算子 | 作用位置 | 改写 |
|---|---|---|---|
| ROR | 关系算子替换 | BINARY_OPERATOR 的 `<` `<=` `>` `>=` `==` `!=` | `<`↔`<=`、`>`↔`>=`、`==`↔`!=` |
| OBO | 差一 | 比较或下标里的整数字面量 n | `n+1` 或 `n-1`（seed 决定） |
| NEG | 条件取反 | IF_STMT / WHILE_STMT / FOR_STMT 的条件 | `c` → `!(c)` |
| LOR | 逻辑算子替换 | `&&` ↔ `\|\|` | |
| AOR | 算术算子替换 | `+`↔`-`、`*`↔`/`（整型与指针加减都允许） | |
| DGS | 删守卫 | 形如 `if (cond) return …;` / `if (cond) { return …; }` / `if (cond) break;` 的单语句 if | 整段删除 |
| DST | 删语句 | 函数体内一条赋值、自增或调用表达式语句（不删 return、不删声明） | 整条删除 |
| RVR | 返回值替换 | `return expr;`（expr 不是字面量 0 / NULL） | `return 0;` 或 `return NULL;`（按返回类型） |

每个算子实现为 `find_sites(func_cursor) -> list[Site]` 与 `apply(src_bytes, site, rng) -> bytes`；Site 记录算子、字节区间、原文本、序号。变异后的函数必须能用 libclang 零 error 重新解析，否则该候选作废。

## 4. 变异体选择与 kill 检查

```
for target in 入选目标:
    for level in L0..L3:                       # L0 先选
        若函数有注释：去注释后的原函数放回副本，项目测试必须通过，否则标 strip_unsafe，该 (target, level) 不出题、也不当 L1–L3 的参照
        sites = 所有算子在该级目标函数上的候选位点，按 (算子优先序, 位点序号) 排序
        order = rng(seed, target_id).shuffle(sites)          # 种子里没有级别
        若 L0 已选定位点 s0：把 s0 在本级的对应位点排最前（L1 精确对应，L2 / L3 靠记号对齐），再把算子为 op0 的位点排在前面
        for site in order:
            mutant = apply(site)
            若重新解析有 error：跳过
            ev = evaluate(mutant 作为候选)      # 沙箱：必须编译通过，且在测试阶段失败
            若 ev.stage == 'test' 且 category ∈ {test_fail, runtime_crash, runtime_timeout}：
                复核：再评测一次，第二次仍在测试阶段失败 → 选定，记录 kill_mode 与 kill_recheck；break
                           第二次没失败 → 计入 unstable_count，继续下一个位点
            否则（编译失败 / 测试仍通过 = 等价变异体）：计数后继续
        若没有任何位点被杀死：该 (target, level) 标 no_killed_mutant，不出题
```

- 优先序：ROR、NEG、LOR、OBO、DGS、AOR、RVR、DST（前面的更像真实缺陷、更少产生等价变异体）。
- 跨级别一致性：L1–L3 先试 L0 选定位点的对应位点，选中的记 `same_site_as_L0`，再优先复用 L0 的算子，记 `same_operator_as_L0`。**「四级同算子」的目标子集恒等于「四级都出了题」，不构成对照**；报告里的可比子集是「四级同一个位点、且提示词上下文没有被裁条目」的目标（第 12 节 #18、#20）。
- 一个 (target, level) 只出一个变异体。
- 变异体 kill 检查最多尝试 12 个位点，超过则放弃该 (target, level) 并计数（控制沙箱成本：208 × 4 × ≤12 次 evaluate，复核另外多一次）。

## 5. Prompt

system：You are an experienced C programmer. The function below contains a bug that makes the project's tests fail. Return the corrected function only, as one ```c code block containing the complete definition. Keep the signature. Do not add #include lines. No explanation.

user：依赖上下文（与生成任务相同的小节格式与顺序）→ `Buggy function:` → 代码块 → 约束行（C 标准、禁止的头与调用）。模板常量与 `PROMPT_VERSION`、`PROMPT_DIGEST` 分开命名（`REPAIR_PROMPT_VERSION = "repair-v2"`、`REPAIR_PROMPT_DIGEST`）。user 消息里的「项目上下文」小节与生成任务由同一段文本 `CONTEXT_BLOCK` 拼出；函数文本里带着注释时 `build_repair_messages` 直接报错（最后一道关）。

## 6. 评测与指标

- 与生成任务共用 evaluate / attribute / similarity；结果记录增加 `task: "repair"`、`mutation: {operator, site_index, original_text, mutated_text}`、`kill_mode`、`same_operator_as_L0`、`same_site_as_L0`、`context_orphans`、`unchanged`（候选与变异体规范化后相同，即模型什么也没改）、`restored`（候选与该级原函数规范化后相同，即逐字还原）。
- 指标：按 model × level（× corpus）的通过率、归因分布、`unchanged` 率、`restored` 率、候选与原函数的相似度；**可比子集**（四级同一个位点、上下文没有被裁条目）的通过率单独给表，另给「只留本级与 L0 同一个缺陷的配对」相对 L0 的变化；按变异体怎么死的（`kill_mode`）、按目标被零值桩杀死的方式（`stub_kill_mode`）、按上下文有没有被裁条目、按算子分层的通过率。
- `unchanged` 的候选却通过了项目测试，说明变异体没有被测试稳定地杀死：这道题整题（所有模型、所有样本）从统计里剔除，报告开头点名，`evaluate` 阶段同样提示并失败。
- 生成任务与修复任务在 summary 里是两张并列的表，报告开头说明两者的输入差异。

## 7. 数据文件

- `results/mutants-<corpus>-<level>.jsonl`：target_id、level、operator、site_index、original_text、mutated_text、mutant_code（完整函数）、kill_mode、kill_recheck、tried_sites、equivalent_count、compile_fail_count、unstable_count、same_operator_as_L0、same_site_as_L0、anchor、context_orphans、input hashes。

## 8. 模块与接口

```python

# bench/prompt.py（新增）
REPAIR_PROMPT_VERSION, REPAIR_PROMPT_DIGEST

# bench/pipeline.py / cli.py（新增阶段与参数）

```

MockLLM 增加四种 repair 用模式：`oracle` 对 repair 任务返回该级原函数（必须 100% pass）；`unchanged` 返回变异体原样（必须 100% 不通过且 unchanged=True）；`reformat` 返回原函数换排版加注释（必须 100% pass 且 restored=True、unchanged=False）；`touched` 返回变异体加一条无害语句（必须 100% 不通过，unchanged 与 restored 都为假）。

## 11. 局限（写进 README）

与 `bench/limitations.py` 的同一份内容（README 第 8 节、报告的「局限」一节同源），这里列修复任务相关的几条：

- 变异体是人工注入的单点缺陷，不等于真实缺陷分布；不同级别的变异体不一定是同一个缺陷：L1 位点一一对应，L2 / L3 靠记号对齐，对不上的退回到复用算子；只有可比子集上的级别差异才不混入缺陷位置的差异，「四级同算子」子集恒等于全集，不是对照。
- 不给测试输出，难度高于真实场景中的修复，通过率绝对值不可与其它基准比较，只看级别间的差异。
- 崩溃型与超时型杀死的目标，测试可能不检查返回内容。报告给两个口径的分层：变异体怎么死的（`kill_mode`）和目标被零值桩杀死的方式（`stub_kill_mode`），两者不等价，要两张表一起看。
- 提示词上下文按注入缺陷后的函数裁剪过（只裁原型、宏、全局，类型定义不裁）；被裁条目的题不进可比子集，通过率单列。
- 修复任务的相似度和 `restored` 率不是记忆指标；NEG 缺陷（固定改成 `!(c)`）的显眼程度随级别变化；字符串字面量里的项目词汇去不掉（目标自己的原名出现在字面量里的题作废）。

实现阶段确认的偏差，以及两路评审（正确性可信度、质量）对修复任务提出的问题和处理结果。「处理」一列：改文档 = 现行做法更合理，以此为准；补充 = 本附录原来没有规定，现补上；改代码 = 契约更合理，代码已改。#18 以后是评审之后新增的条目。

| 5 | 位点界定 | 各算子的作用位置（§3） | OBO 只改十进制整数字面量（范围：比较操作数、数组下标，以及沿括号、强制转换和加减法能走到的字面量），0 只 +1（下标 -1 是未定义行为，杀不杀死不可复现）；DGS / DST 只认直接位于复合语句里的语句（`else if` 链里的 if、没有花括号的循环体不认），DGS 要求无 else 且 then 分支是单条 return / break；AOR 只改二元 `+ - * /`（不含 `+=`），类型上必然非法的指针运算（指针相减、整数 + 指针、指针乘除）不算位点；RVR 只处理返回 scalar / 指针的函数，指针返回在 `NULL` 有定义时写 `NULL` 否则写 `0`；NEG 对没有条件的 `for (;;)` 不出位点；宏实参里的、宏生成的、范围里含预处理指令行的位点一律不要 | 补充 |
