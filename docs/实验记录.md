# 实验记录 · 真实语料的集成检查

2026-10-27。对 9 个真实语料依次跑 prepare → coverage → targets → obfuscate（L0–L3 四级副本）→ verify（oracle gate），确认流水线在真实代码上成立，
并把结果落档，给以后复核留一份可对照的基线（设计文档第 7 节的要求）。

**范围**：只到 verify。没有调用任何模型，所以这里没有通过率、相似度之类的数字；那些由 `python3 -m bench report` 在真实模型跑完后产出（README 第 9 节）。

## 1. 结论

- **9 个语料全部走通，没有语料被剔出 v1 目标集，这次也没有改 spec 或代码。** prepare 在沙箱里构建并通过项目测试 9/9；
  coverage 没有 gcov 失败；36 个混淆副本（9 个语料 × L0–L3）的 verify 全部通过；832 次 oracle gate 通过 832 次。
- **v1 目标总数 208 个，四级（L0–L3）任务总数 832 个**（208 × 4）。
- **总耗时 14 分 15 秒**（855 秒，冷启动，`--jobs 8`，16 核 / 15 GB 的机器；其中 targets 5 分 32 秒（主要是 stub-kill），verify 6 分 51 秒）。
- **同一份代码、同一个 seed，换并发度重跑，产出逐项一致，只有一处标签不同**：mpc 的 `mpcaf_grammar_string` 在零值桩下会让测试程序不终止并不断吃内存，
  被超时杀掉还是被 OOM 杀掉取决于谁先到，所以它的杀死方式在两次运行里一次是 `runtime_timeout`、一次是 `test_fail`（第 7 节）；第 8 节的重跑又发现 mpc 的
  `mpcaf_grammar_char` 同样抖动。这是设计文档里记过的「OOM 与超时的归因随负载抖动」，不影响目标集，只影响这两个目标在报告里归入哪个分层。
- **负向对照**：208 个目标在 L0–L3 四级副本里各换成一次零值桩，共 832 次，项目测试全部失败（832 / 832 被杀死）：混淆没有削弱测试对这些函数的灵敏度（第 8 节）。

## 2. 怎么跑的

```bash
export CORPUS_MIRROR=<放着 9 个浅克隆的目录>      # 可选；不设置就按 spec 的 url + commit 联网克隆
python3 -m bench prepare   --jobs 8 --seed 20261027
python3 -m bench coverage  --jobs 8 --seed 20261027
python3 -m bench targets   --jobs 8 --seed 20261027     # TargetFilter 取默认值，见下
python3 -m bench obfuscate --jobs 8 --seed 20261027     # 默认 L0–L3 四级；L0 是原样副本，用来跑 L0 的 oracle gate
python3 -m bench verify    --jobs 8 --seed 20261027     # oracle gate：每个入选目标在每一级用原函数体跑一遍完整 evaluate
python3 -m bench.experiment_record --update docs/实验记录.md
```

* **oracle gate 就是 `verify` 命令**，没有另外的 `oracle` 子命令：它对每个级别的每个入选目标，把混淆副本里该目标的原函数文本当作候选，
  走一遍和模型回复完全相同的 evaluate（替换 → 语法检查 → 构建 → 项目测试 → 归因），必须得到 `pass`。
* TargetFilter 默认值：`min_statements=3`、`min_lines=4`、`max_lines=120`、`max_per_corpus=50`、`require_exec=True`、`require_stub_kill=True`；
  stub-kill 用 `scan_all`（命令行默认）：所有候选都做，才能报出整个语料「测试覆盖不住」的函数数，入选的目标与不开时完全相同。
* 沙箱：`gcc:13`（镜像 ID 见下面生成区），每个容器 1 个 CPU、1 GB 内存、256 个进程，`--jobs 8` 即同时最多 8 个容器。
* **冷启动**：在一个空的工作区（`--workspace`）里从头跑，语料从本地浅克隆复制，结果、副本、临时目录都是新建的，没有任何缓存可用。
  跑完把上一次运行的 `results/`、`corpus/src`、`tmp/obf` 备份走，把这次的产出换进默认目录，再把上面五条命令各跑一遍（不带 `--workspace`）：
  全部显示「跳过(输入未变)」（五条命令合计约 1.2 秒，产出换了位置，输入哈希仍然对得上）。
* 「总耗时」是五条命令的墙钟时间之和（含 Python 进程启动、libclang 初始化），不含这之后的补充检查。

## 6. 怎么读这些数字

1. **链路在 9 个真实语料上都成立。** prepare 在沙箱里构建并通过项目测试 9/9；coverage 没有 gcov 失败；36 个副本的 verify 全部通过；
   208 个目标 × 4 级 = 832 次 oracle gate 全部通过；符号混淆没有一次需要回退到 strict；L2、L3 的变换没有一次被回滚。
2. **目标集。** 提取 702 个函数，454 个过了静态过滤，390 个同时被项目测试执行过（候选），入选 208 个。
   cjson、mpc、parson 达到每个语料 50 个的名额上限（144 个杀得死的候选因名额已满没入选，按 seed 抽样落选）；
   其余语料入选的是全部杀得死的候选。parson、mpc、cjson 三个语料占 150 / 208 = 72% 的目标，
   汇总数字会被它们主导，读结果时要同时看分语料的表。
3. **测试覆盖不住的函数。** 38 个候选在零值桩下项目测试仍然通过（mpc 21、cjson 14、parson 2、tinyexpr 1），按设计不入选；这是这几个库自带测试的盲区，不是流水线的问题。
4. **杀死方式。** 208 个入选目标里，160 个（77%）是断言失败（test_fail），45 个（22%）是桩让测试程序崩溃（runtime_crash），
   3 个（1%）是超时（runtime_timeout，cjson 2、tinyexpr 1）。崩溃型集中在 parson 21/50、cjson 9/50、sds 9/16、vec 4/6、inih 1/5、jsmn 1/5。
   这些目标的测试没有断言函数返回了什么，任何不崩溃的错误实现都能通过，通过率会被高估，所以报告按杀死方式分层给通过率，读结果时优先看 test_fail 型。
   另外 test_fail 里有 2 个 mpc 目标（`mpcaf_grammar_string`、`mpcaf_grammar_char`）按行为是不终止地吃内存，会被超时或 OOM 杀掉，标签不稳定，
   按行为应当算 runtime_timeout 型，见第 7、8 节。
5. **字符串化宏。** 库自己的源码里被 `#` 宏字符串化的拼写一律不改名；测试文件里的默认照常改名，改了多少写在「字符串化实参被改名」一列：
   cjson 163、parson 91、mpc 52、vec 17、tiny-regex-c 1，其余（inih、jsmn、sds、tinyexpr）为 0，合计 324。这些名字被字符串化后的输出文字随之变化，
   而项目测试不逐字比对这类文字，所以 verify 通过不能说明这部分输出与原件一致；要连这部分一起保持，用 `obfuscate --strict-stringify on`（排除数会大幅上升）。
6. **泄漏检查的放行。** 项目标识符里有一部分是常见英文词，描述里出现它们不算泄漏（但会记录）：cjson 709 个里放行 106 个，mpc 600 个里放行 86 个，tinyexpr 199 个里放行 55 个。
   入选目标自己的函数名落在放行集合里的有 5 个（cjson 的 `print`，tinyexpr 的 `base`、`binary`、`match`、`power`）：这几个目标的描述里写出函数名不会触发重试，只会记进描述记录的 `own_name_hit`，报告里统计。
7. **变换覆盖。** L2 应用 322 次（候选位置 635 个），L3 应用 1450 次（候选 1843 个，其中 opaque 语句 1077 条占大头）。
   候选位置之所以多于应用次数，一是按 ratio 抽样，二是被跳过：L2 跳过 1004 个（macro_generated 818、macro 124、rhs_side_effect 28、lhs_not_simple 24、has_continue 8、directive_in_gap 2），L3 跳过 733 个（操作数不是原子表达式 465、范围含宏调用 / 预处理指令 / 内建宏 99、操作数类型不是算术类型 91、操作数类型不是整型 77、两侧文本相同 1）。
   宏生成的语句、宏参数里的位置、`#if` 劈开的位置一律不动，所以宏用得重的库（cjson 的 Unity 断言宏、parson、vec）可改的位置明显少于理论候选数，见 README 局限 6。

## 7. 稳定性：同一个 seed 重跑，哪些一样，哪些不一样

### 7.1 与上一次运行逐项比较

上一次运行是同一天早些时候的 `--jobs 6`（产出已备份，不入库）。把两次的 `results/` 下 72 个数据文件逐项比较，忽略时间戳和耗时：

* **逐项一致（70 个文件）**：提取 / 候选 / 入选个数、入选目标的 id 与顺序、每个函数的 gcov 执行次数、各目标的 stub-kill 判定（杀死还是存活）、
  36 个副本的改名表、L1 / L2 / L3 的变换统计、副本源码树哈希、副本 verify 与 oracle gate 的结果（含通过的目标 id）、各阶段的输入哈希。
  也就是说 `--jobs 6` 和 `--jobs 8` 选出同一批目标，生成同样的副本。
* **有差异（2 个文件）**：`targets-mpc.jsonl` 里 `mpc:mpc.c:mpcaf_grammar_string` 的 `stub_kill_mode`（上次 `runtime_timeout`，这次 `test_fail`），
  以及 `targets-mpc.summary.json` 里对应的两个计数（`test_fail` 49 → 50、`runtime_timeout` 1 → 0）。除此之外没有任何差异。

### 7.2 mpc 的两个目标：杀死方式随负载抖动

两次运行之间标签不同的是 `mpcaf_grammar_string`，下面先讲它；`mpcaf_grammar_char` 在第 8 节的重跑里表现出同样的抖动。

`mpcaf_grammar_string` 的零值桩（`{ return 0; }`）让后面的语法解析进入不会终止、并且不断分配内存的状态（具体卡在哪一步没有深究）。沙箱里这个容器有两个上限，谁先到谁杀它：
30 秒超时（`timeout -s KILL`）和 1 GB 内存上限（`--memory-swap` 与 `--memory` 相同，超限直接 OOM）。哪个先到取决于那一刻的 CPU 争用。

* 同一份桩在沙箱里重复跑 16 次（并发 8）：10 次超时（约 30.5 秒，记 `timed_out`），6 次在 25 到 26 秒被杀、没有超时标记。
* 再跑 8 次，这次保留容器（去掉 `--rm`）用 `docker inspect` 核对：7 次是超时（约 30.8 秒，`OOMKilled=false`，退出码 137），1 次 `OOMKilled=true`（24.5 秒，退出码 137）。
* `mpcaf_grammar_char` 用同样的方法跑 8 次（并发 8，保留容器）：8 次都是 `OOMKilled=true`，约 17 秒被杀；但它在第 8 节 L0 的重跑里却跑满了 30 秒超时。
  两个目标都是不终止地吃内存，吃到 1 GB 要 17 到 30 多秒，用时受并发负载影响，所以结局会变。
* 归因规则（设计文档 4.12）：超时记 `runtime_timeout`；退出码 137 但没到超时的（OOM）信号是 SIGKILL，不在崩溃信号集合 `{SIGSEGV, SIGABRT, SIGFPE, SIGBUS}` 里，记 `test_fail`。
  所以同一个目标两种结局对应两个标签。
* 三次完整的 targets 运行里，这个目标的标签是 `runtime_timeout`（评审修复前那次）、`runtime_timeout`（上一次）、`test_fail`（这次，`results/` 里记的就是这个）；
  `mpcaf_grammar_char` 在这三次里都是 `test_fail`。

两种结局项目测试都失败，这个目标在每次运行里都是「杀得死」，所以目标集不变；变的只是它在报告里归入哪个杀死方式分层。
第 8 节的 832 次重跑里，`mpcaf_grammar_char` 在 L0 是 `runtime_timeout`、在 L1–L3 是 SIGKILL 型的 `test_fail`（见 8.2）。其余 8 个语料每个目标的标签在 5 次观察
（targets 阶段 + L0–L3 重跑）里完全一致，包括 3 个 `runtime_timeout`（cjson 2 个、tinyexpr 1 个）。
这是设计文档记过的「OOM 与超时的归因随负载抖动」在真实语料上的实际表现，这次不改规则，只如实记下。

### 7.3 与评审修复前的那次全链路比较

评审修复之前我在同一批语料上用 MockLLM 跑过一遍全链路（工作区 `tmp/integ/real`，不入库）。和这次的 `results/` 对比：

* 入选目标（每个语料的 id 集合与顺序）完全一致，杀死方式的分布除了 mpc 那个不稳定的标签（7.2）外也一致；
* L1 的改名数只有两处不同：inih 64 → 61、sds 150 → 143，正好对应字符串化实参被改名数 3 → 0、7 → 0。原因是修复后库自己的源码里被 `#` 宏字符串化的拼写一律不改名，
  以前这两个库里有几个是改了的（设计文档第 10 节第 9 条）；
* L3 副本的源码树哈希 9 个语料全部变了：opaque 语句的变量名改走 L1 的取名规则（形如 `v_<n>`），不再是固定模式的 `_k<数字>`（第 10 节第 10 条）；

## 8. 补充检查：零值桩在 L0–L3 副本里的表现（负向对照）

### 8.2 不稳定的两个目标

mpc 的 `mpcaf_grammar_string` 与 `mpcaf_grammar_char` 的标签在不同观察之间来回变（7.2 讲了原因：不终止地吃内存，超时与 OOM 谁先到）：

| `mpcaf_grammar_char` | test_fail | runtime_timeout | test_fail（SIGKILL，未到超时） | test_fail（SIGKILL，未到超时） | test_fail（SIGKILL，未到超时） |

`SIGKILL 但没到超时` 的次数（OOM 型，记成 test_fail）：L1 有 2 次、L2 有 2 次、L3 有 1 次，都是这两个目标。
**这两个目标按行为应当算 `runtime_timeout` 型（测试没有断言返回值，只是因为程序不终止而被杀）**，但记录里是 `test_fail`；读 test_fail 分层的结果时，
可以把它们当作不确定的两个（占 test_fail 型目标 160 个中的 2 个）。

### 8.3 这个检查证明了什么、没证明什么

证明的：零值桩（返回 0 / 空函数体）在四级副本里都会让项目测试失败，L1–L3 的改名与改写没有把这些测试变成空转。
没证明的：零值桩是最粗的一种错误实现，杀得死不等于测试能分辨所有错误实现；崩溃型和超时型杀死的目标本来就不断言返回值（3.2）。

## 9. 这份记录的局限

- 符号混淆的改名表依赖宿主机上 libclang 看到的系统头和借来的内置头目录（生成区「环境与来源」里的内置头摘要），换一台机器或升级系统后，同一个 seed 的改名数可能不同；
  混淆结果的输入哈希里带了这份摘要，环境变了旧副本会被判为过期。
- 「代码摘要」只覆盖影响该阶段产出的 `bench/` 源文件；文档、测试、本模块的改动不改变它们。
- 杀死方式的标签对「不终止并持续吃内存」的目标不稳定（第 7.2 节）：它们是被超时杀掉还是被 OOM 杀掉，取决于机器负载，两种结局在项目测试里都算被杀死，
  所以目标集不受影响，受影响的只是分层标签。设计文档把 OOM 归 `test_fail` 是有意的取舍，这里只是把它在真实语料上的实际表现记下来。
- 第 3 节里「exec>0」「过静态过滤」「解析 error」三列的口径是本文件定的（见 3.1 的说明），数据文件里没有直接存这几个数，是用同一份提取结果与 coverage 数据重新算的，
  算它们的脚本放在 `tmp/`、不入库；其余列直接来自 `results/` 下的数据文件。第 8 节的负向对照同样是 `tmp/` 下的一次性脚本（只调用 `bench.targets` 里已有的函数），没有并进 CLI。
