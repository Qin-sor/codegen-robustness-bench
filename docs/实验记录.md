# 实验记录 · 真实语料的集成检查

2026-10-27（第 10 节在评审修复之后于 2026-10-28 重跑）。对 9 个真实语料依次跑 prepare → coverage → targets → obfuscate（L0–L3 四级副本）→ verify（oracle gate），确认流水线在真实代码上成立，
并把结果落档，给以后复核留一份可对照的基线（设计文档第 7 节的要求）；缺陷修复任务新增的 mutate 阶段与回放复核的结果在第 10 节（评审修复之后重跑过，第 10 节的数据是新的）。

**范围**：到 verify，加上缺陷修复任务的 mutate 与回放复核（第 10 节）。没有调用任何真实模型，所以这里没有通过率、相似度之类的数字；那些由 `python3 -m bench report` 在真实模型跑完后产出（README 第 9 节）。
第 10.3 节的回放复核（`check-mutants`）把出题的变异体和去注释的原函数在沙箱里再评测一遍，验证的是出题，不是模型的成绩。

## 1. 结论

- **9 个语料全部走通，没有语料被剔出 v1 目标集，为此没有改过 spec 或代码。**（评审修复改动了 `bench/` 的代码，之后重跑的数据在第 10 节，prepare 到 verify 的重跑结果与改动前一致。）prepare 在沙箱里构建并通过项目测试 9/9；
  coverage 没有 gcov 失败；36 个混淆副本（9 个语料 × L0–L3）的 verify 全部通过；832 次 oracle gate 通过 832 次。
- **v1 目标总数 208 个，四级（L0–L3）任务总数 832 个**（208 × 4）。
- **缺陷修复任务的 mutate**（评审修复之后的第二轮，第 10 节）：832 个（目标, 级别）全部出了题、放弃 0 个，复核不稳定 0 个，22 分 7 秒（`--jobs 8`）；
  L1 选中的就是 L0 的那个位点（208 / 208），L2 199 / 208（95.7%），L3 183 / 208（88.0%）；四级同一个位点且上下文没有被裁条目的可比子集是 150 个目标。
  四级同算子的目标数恒等于全集（208 / 208），不构成对照。
- **总耗时 14 分 15 秒**（855 秒，冷启动，`--jobs 8`，16 核 / 15 GB 的机器；其中 targets 5 分 32 秒（主要是 stub-kill），verify 6 分 51 秒）。
- **同一份代码、同一个 seed，换并发度重跑，产出逐项一致，只有一处标签不同**：mpc 的 `mpcaf_grammar_string` 在零值桩下会让测试程序不终止并不断吃内存，
  被超时杀掉还是被 OOM 杀掉取决于谁先到，所以它的杀死方式在两次运行里一次是 `runtime_timeout`、一次是 `test_fail`（第 7 节）；第 8 节的重跑又发现 mpc 的
  `mpcaf_grammar_char` 同样抖动。这是设计文档里记过的「OOM 与超时的归因随负载抖动」，不影响目标集，只影响这两个目标在报告里归入哪个分层。
- **负向对照**：208 个目标在 L0–L3 四级副本里各换成一次零值桩，共 832 次，项目测试全部失败（832 / 832 被杀死）：混淆没有削弱测试对这些函数的灵敏度（第 8 节）。

## 2. 怎么跑的

```bash
export CORPUS_MIRROR=<放着 9 个浅克隆的目录>      # 可选；不设置就按 spec 的 url + commit 联网克隆
python3 -m bench prepare   --jobs 8 --seed 20261027
python3 -m bench coverage  --jobs 8 --seed 20261027
python3 -m bench targets   --jobs 8 --seed 20261027     # TargetFilter 取默认值，见下
python3 -m bench obfuscate --jobs 8 --seed 20261027     # 默认 L0–L3 四级；L0 是原样副本，用来跑 L0 的 oracle gate
python3 -m bench verify    --jobs 8 --seed 20261027     # oracle gate：每个入选目标在每一级用原函数体跑一遍完整 evaluate
python3 -m bench.experiment_record --update docs/实验记录.md
```

* **oracle gate 就是 `verify` 命令**，没有另外的 `oracle` 子命令：它对每个级别的每个入选目标，把混淆副本里该目标的原函数文本当作候选，
  走一遍和模型回复完全相同的 evaluate（替换 → 语法检查 → 构建 → 项目测试 → 归因），必须得到 `pass`。
* TargetFilter 默认值：`min_statements=3`、`min_lines=4`、`max_lines=120`、`max_per_corpus=50`、`require_exec=True`、`require_stub_kill=True`；
  stub-kill 用 `scan_all`（命令行默认）：所有候选都做，才能报出整个语料「测试覆盖不住」的函数数，入选的目标与不开时完全相同。
* 沙箱：`gcc:13`（镜像 ID 见下面生成区），每个容器 1 个 CPU、1 GB 内存、256 个进程，`--jobs 8` 即同时最多 8 个容器。
* **冷启动**：在一个空的工作区（`--workspace`）里从头跑，语料从本地浅克隆复制，结果、副本、临时目录都是新建的，没有任何缓存可用。
  跑完把上一次运行的 `results/`、`corpus/src`、`tmp/obf` 备份走，把这次的产出换进默认目录，再把上面五条命令各跑一遍（不带 `--workspace`）：
  全部显示「跳过(输入未变)」（五条命令合计约 1.2 秒，产出换了位置，输入哈希仍然对得上）。
* 「总耗时」是五条命令的墙钟时间之和（含 Python 进程启动、libclang 初始化），不含这之后的补充检查。

## 6. 怎么读这些数字

1. **链路在 9 个真实语料上都成立。** prepare 在沙箱里构建并通过项目测试 9/9；coverage 没有 gcov 失败；36 个副本的 verify 全部通过；
   208 个目标 × 4 级 = 832 次 oracle gate 全部通过；符号混淆没有一次需要回退到 strict；L2、L3 的变换没有一次被回滚。
2. **目标集。** 提取 702 个函数，454 个过了静态过滤，390 个同时被项目测试执行过（候选），入选 208 个。
   cjson、mpc、parson 达到每个语料 50 个的名额上限（144 个杀得死的候选因名额已满没入选，按 seed 抽样落选）；
   其余语料入选的是全部杀得死的候选。parson、mpc、cjson 三个语料占 150 / 208 = 72% 的目标，
   汇总数字会被它们主导，读结果时要同时看分语料的表。
3. **测试覆盖不住的函数。** 38 个候选在零值桩下项目测试仍然通过（mpc 21、cjson 14、parson 2、tinyexpr 1），按设计不入选；这是这几个库自带测试的盲区，不是流水线的问题。
4. **杀死方式。** 208 个入选目标里，160 个（77%）是断言失败（test_fail），45 个（22%）是桩让测试程序崩溃（runtime_crash），
   3 个（1%）是超时（runtime_timeout，cjson 2、tinyexpr 1）。崩溃型集中在 parson 21/50、cjson 9/50、sds 9/16、vec 4/6、inih 1/5、jsmn 1/5。
   这些目标的测试没有断言函数返回了什么，任何不崩溃的错误实现都能通过，通过率会被高估，所以报告按杀死方式分层给通过率，读结果时优先看 test_fail 型。
   另外 test_fail 里有 2 个 mpc 目标（`mpcaf_grammar_string`、`mpcaf_grammar_char`）按行为是不终止地吃内存，会被超时或 OOM 杀掉，标签不稳定，
   按行为应当算 runtime_timeout 型，见第 7、8 节。
5. **字符串化宏。** 库自己的源码里被 `#` 宏字符串化的拼写一律不改名；测试文件里的默认照常改名，改了多少写在「字符串化实参被改名」一列：
   cjson 163、parson 91、mpc 52、vec 17、tiny-regex-c 1，其余（inih、jsmn、sds、tinyexpr）为 0，合计 324。这些名字被字符串化后的输出文字随之变化，
   而项目测试不逐字比对这类文字，所以 verify 通过不能说明这部分输出与原件一致；要连这部分一起保持，用 `obfuscate --strict-stringify on`（排除数会大幅上升）。
6. **泄漏检查的放行。** 项目标识符里有一部分是常见英文词，描述里出现它们不算泄漏（但会记录）：cjson 709 个里放行 106 个，mpc 600 个里放行 86 个，tinyexpr 199 个里放行 55 个。
   入选目标自己的函数名落在放行集合里的有 5 个（cjson 的 `print`，tinyexpr 的 `base`、`binary`、`match`、`power`）：这几个目标的描述里写出函数名不会触发重试，只会记进描述记录的 `own_name_hit`，报告里统计。
7. **变换覆盖。** L2 应用 322 次（候选位置 635 个），L3 应用 1450 次（候选 1843 个，其中 opaque 语句 1077 条占大头）。
   候选位置之所以多于应用次数，一是按 ratio 抽样，二是被跳过：L2 跳过 1004 个（macro_generated 818、macro 124、rhs_side_effect 28、lhs_not_simple 24、has_continue 8、directive_in_gap 2），L3 跳过 733 个（操作数不是原子表达式 465、范围含宏调用 / 预处理指令 / 内建宏 99、操作数类型不是算术类型 91、操作数类型不是整型 77、两侧文本相同 1）。
   宏生成的语句、宏参数里的位置、`#if` 劈开的位置一律不动，所以宏用得重的库（cjson 的 Unity 断言宏、parson、vec）可改的位置明显少于理论候选数，见 README 局限 6。

## 7. 稳定性：同一个 seed 重跑，哪些一样，哪些不一样

### 7.1 与上一次运行逐项比较

上一次运行是同一天早些时候的 `--jobs 6`（产出已备份，不入库）。把两次的 `results/` 下 72 个数据文件逐项比较，忽略时间戳和耗时：

* **逐项一致（70 个文件）**：提取 / 候选 / 入选个数、入选目标的 id 与顺序、每个函数的 gcov 执行次数、各目标的 stub-kill 判定（杀死还是存活）、
  36 个副本的改名表、L1 / L2 / L3 的变换统计、副本源码树哈希、副本 verify 与 oracle gate 的结果（含通过的目标 id）、各阶段的输入哈希。
  也就是说 `--jobs 6` 和 `--jobs 8` 选出同一批目标，生成同样的副本。
* **有差异（2 个文件）**：`targets-mpc.jsonl` 里 `mpc:mpc.c:mpcaf_grammar_string` 的 `stub_kill_mode`（上次 `runtime_timeout`，这次 `test_fail`），
  以及 `targets-mpc.summary.json` 里对应的两个计数（`test_fail` 49 → 50、`runtime_timeout` 1 → 0）。除此之外没有任何差异。

### 7.2 mpc 的两个目标：杀死方式随负载抖动

两次运行之间标签不同的是 `mpcaf_grammar_string`，下面先讲它；`mpcaf_grammar_char` 在第 8 节的重跑里表现出同样的抖动。

`mpcaf_grammar_string` 的零值桩（`{ return 0; }`）让后面的语法解析进入不会终止、并且不断分配内存的状态（具体卡在哪一步没有深究）。沙箱里这个容器有两个上限，谁先到谁杀它：
30 秒超时（`timeout -s KILL`）和 1 GB 内存上限（`--memory-swap` 与 `--memory` 相同，超限直接 OOM）。哪个先到取决于那一刻的 CPU 争用。

* 同一份桩在沙箱里重复跑 16 次（并发 8）：10 次超时（约 30.5 秒，记 `timed_out`），6 次在 25 到 26 秒被杀、没有超时标记。
* 再跑 8 次，这次保留容器（去掉 `--rm`）用 `docker inspect` 核对：7 次是超时（约 30.8 秒，`OOMKilled=false`，退出码 137），1 次 `OOMKilled=true`（24.5 秒，退出码 137）。
* `mpcaf_grammar_char` 用同样的方法跑 8 次（并发 8，保留容器）：8 次都是 `OOMKilled=true`，约 17 秒被杀；但它在第 8 节 L0 的重跑里却跑满了 30 秒超时。
  两个目标都是不终止地吃内存，吃到 1 GB 要 17 到 30 多秒，用时受并发负载影响，所以结局会变。
* 归因规则（设计文档 4.12）：超时记 `runtime_timeout`；退出码 137 但没到超时的（OOM）信号是 SIGKILL，不在崩溃信号集合 `{SIGSEGV, SIGABRT, SIGFPE, SIGBUS}` 里，记 `test_fail`。
  所以同一个目标两种结局对应两个标签。
* 三次完整的 targets 运行里，这个目标的标签是 `runtime_timeout`（评审修复前那次）、`runtime_timeout`（上一次）、`test_fail`（这次，`results/` 里记的就是这个）；
  `mpcaf_grammar_char` 在这三次里都是 `test_fail`。

两种结局项目测试都失败，这个目标在每次运行里都是「杀得死」，所以目标集不变；变的只是它在报告里归入哪个杀死方式分层。
第 8 节的 832 次重跑里，`mpcaf_grammar_char` 在 L0 是 `runtime_timeout`、在 L1–L3 是 SIGKILL 型的 `test_fail`（见 8.2）。其余 8 个语料每个目标的标签在 5 次观察
（targets 阶段 + L0–L3 重跑）里完全一致，包括 3 个 `runtime_timeout`（cjson 2 个、tinyexpr 1 个）。
这是设计文档记过的「OOM 与超时的归因随负载抖动」在真实语料上的实际表现，这次不改规则，只如实记下。

### 7.3 与评审修复前的那次全链路比较

评审修复之前我在同一批语料上用 MockLLM 跑过一遍全链路（工作区 `tmp/integ/real`，不入库）。和这次的 `results/` 对比：

* 入选目标（每个语料的 id 集合与顺序）完全一致，杀死方式的分布除了 mpc 那个不稳定的标签（7.2）外也一致；
* L1 的改名数只有两处不同：inih 64 → 61、sds 150 → 143，正好对应字符串化实参被改名数 3 → 0、7 → 0。原因是修复后库自己的源码里被 `#` 宏字符串化的拼写一律不改名，
  以前这两个库里有几个是改了的（设计文档第 10 节第 9 条）；
* L3 副本的源码树哈希 9 个语料全部变了：opaque 语句的变量名改走 L1 的取名规则（形如 `v_<n>`），不再是固定模式的 `_k<数字>`（第 10 节第 10 条）；
* L2 副本的哈希除 inih、sds 外不变（它们的 L1 改名表变了）；L0 副本的哈希全部不变（等于原始源码树）。

## 9. 这份记录的局限

- 符号混淆的改名表依赖宿主机上 libclang 看到的系统头和借来的内置头目录（生成区「环境与来源」里的内置头摘要），换一台机器或升级系统后，同一个 seed 的改名数可能不同；
  混淆结果的输入哈希里带了这份摘要，环境变了旧副本会被判为过期。
- 「代码摘要」只覆盖影响该阶段产出的 `bench/` 源文件；文档、测试、本模块的改动不改变它们。
- 杀死方式的标签对「不终止并持续吃内存」的目标不稳定（第 7.2 节）：它们是被超时杀掉还是被 OOM 杀掉，取决于机器负载，两种结局在项目测试里都算被杀死，
  所以目标集不受影响，受影响的只是分层标签。设计文档把 OOM 归 `test_fail` 是有意的取舍，这里只是把它在真实语料上的实际表现记下来。
- 第 3 节里「exec>0」「过静态过滤」「解析 error」三列的口径是本文件定的（见 3.1 的说明），数据文件里没有直接存这几个数，是用同一份提取结果与 coverage 数据重新算的，
  算它们的脚本放在 `tmp/`、不入库；其余列直接来自 `results/` 下的数据文件。第 8 节的负向对照同样是 `tmp/` 下的一次性脚本（只调用 `bench.targets` 里已有的函数），没有并进 CLI。
- 这里只证明链路在这 9 个库上跑得通、副本等价且目标集可复现，不证明任何模型的表现。
- 第 10 节：变异体是人工注入的单点缺陷，不代表真实缺陷的分布；L2 / L3 的「同一个位点」靠记号对齐，对不上的目标（L2 9 个、L3 25 个）退回到只复用算子；
  崩溃型 / 超时型杀死的变异体（28.0%）其测试可能不检查返回内容，报告按变异体怎么死的和目标的桩怎么死的两个口径分层；
  复核在同一并发度下做，只能挡掉一部分偶发情况，runtime_timeout 与 test_fail 的标签在独立运行之间仍会差一两个；字符串字面量里的项目词汇去不掉
  （36 / 624 个变异体，目标自己的原名出现在字面量里的 3 道出题时作废）；提示词上下文按注入缺陷后的函数裁剪，被裁条目的题不进可比子集。
  回放复核（10.3）验证出题的变异体稳定地让测试失败，不证明任何模型的表现。

**这是评审修复之后的第二轮数据。** 第一轮（洗牌种子里带级别、kill 检查只跑一次、提示词上下文取自原函数）的结论被评审推翻了几处，
处理见 `docs/设计-缺陷修复任务.md` 第 12 节里 #18 以后的各条；第一轮的产出已经被这一轮整体取代，下面写的都是新的。

### 10.1 怎么跑的

```bash
python3 -m bench prepare       --jobs 8 --seed 20261027   # store.py 变了，prepare 的代码摘要变化：9 个语料各重新构建并跑一次项目测试
python3 -m bench coverage      --jobs 8 --seed 20261027   # 输入未变，跳过
python3 -m bench targets       --jobs 8 --seed 20261027   # 输入未变，跳过
python3 -m bench obfuscate     --jobs 8 --seed 20261027   # _edits.py / structure.py 变了：36 个副本重建并 verify
python3 -m bench verify        --jobs 8 --seed 20261027   # postprocess / similarity / prompt 变了：oracle gate 重跑 832 次
python3 -m bench mutate        --jobs 8 --seed 20261027   # 本节的主角
python3 -m bench check-mutants --jobs 6 --seed 20261027 --oracle      # 回放复核
python3 -m bench.experiment_record --update docs/实验记录.md
```

* **重建的副本与重构前逐项一致。** `_edits.py` / `structure.py` 抽出共用的括号配对与宏区间是行为不变的重构：36 个副本重建后，源码树哈希、改名表和统计与改动前的
  `results/obf-*.json` 逐个对过，一个都没变（除代码摘要、时间戳和耗时外；对照用的是改动前的备份，没有入库）。`verify` 重跑后 832 / 832 通过。
* `mutate` 只处理 oracle gate 通过的（目标, 级别），变异体当作候选走完整的 evaluate，编译通过且在测试阶段失败、复核（同一份候选再评测一次）仍失败才算杀死，
  每个（目标, 级别）最多试 12 个位点；函数有注释的，先验证去注释后的原函数仍通过项目测试，变异体的函数文本再去注释（10.4）。
  `mutate` 用 `--jobs 8` 总耗时 22 分 7 秒（1327 秒，九个语料依次处理、语料内部目标并发）。第一轮没有复核，是 864.5 秒；多出来的集中在有超时型变异体的语料（见 10.2 的耗时一条），超时型候选的复核要再等一个 `timeout_s`。

### 10.2 结果

* **832 / 832 个（目标, 级别）全部出了题，放弃 0 个，复核不稳定 0 个**（208 个目标 × 4 级）。进沙箱做 kill 检查 943 次（每个（目标, 级别）至少 1 次），
  其中等价变异体（编译通过、测试仍全过）111 次，编译失败 0 次，重新解析有新 error 而没进沙箱 0 次；复核 832 次，去注释后的原函数复验 200 次（0 次不通过）；
  可改位点合计 14506 个。按级别是 L0 313 次（105）、L1 208 次（0）、L2 210 次（2）、L3 212 次（4）（括号里是其中的等价变异体）。第一轮是 1036 次、其中 204 次等价变异体：L1–L3 现在先试 L0 选定位点的对应位点，那个位点在 L0 已经被杀死，所以等价变异体少了很多。
* **同一个位点（`same_site_as_L0`）**：L1 208 / 208（改名不改位点表，对应是精确的），L2 199 / 208（95.7%），L3 183 / 208（88.0%）；L2 / L3 对不上的是位点的记号被结构 / 语义变换改掉的
  （`x == 0` 换成 `!x`、`a < b` 换成 `b > a`、`if` / `else` 交换后的条件），这些目标退回到只复用算子。生成区「L0 位点在本级的去向」给出 chosen / tried / no_image 的构成，
  「与 L0 选中同一个（算子, 算子内序号）的比例」是同样的统计换成评审用的口径：L1 是 100%，评审在第一轮数据上算出的是 116 / 208（约 56%），第一轮文档里的 35 / 34 / 33 个是把
  `original_text` 也算进相等条件的结果，L1 改名必然让原文不同，严重低估。
* **可比子集**（四级同一个位点、提示词上下文又没有被裁条目）：150 个目标（占 208 个目标的 72.1%），其中四级同位点 183 个、四级上下文都干净 171 个；
  「与 L0 配对可比」的目标数 L1 / L2 / L3 是 171 / 162 / 150。**四级同算子的目标数是 208 个，恒等于四级都出了题的目标数**（复用算子保证了这一点），所以它不构成对照，
  第一轮报告里「最可比的口径」的说法作废。
* **算子分布**（每级 208 个，四级完全相同）：DST 58、RVR 41、NEG 39、ROR 32、LOR 12、DGS 11、AOR 8、OBO 7。四个级别的算子分布完全相同（见生成区），因为每个目标四级都落在同一个算子上。
* **杀死方式**：test_fail 599、runtime_crash 223、runtime_timeout 10；崩溃型与超时型合计 233 / 832（28.0%）。第一轮四个级别的杀死方式分布各不相同，现在几乎一致
  （同一个缺陷在各级的死法相同）。四级杀死方式不全相同的目标有 3 个：1 个四级选中的是同一个位点，死法的差别来自运行时：`mpcaf_grammar_string`（L0–L3：test_fail / runtime_timeout / runtime_timeout / test_fail），它不终止并持续吃内存，被超时杀掉还是被 OOM 杀掉取决于谁先到（同第 7.2 节）；2 个是 L2 / L3 没选中同一个位点，那本来就是不同的缺陷：`mpcf_re_range`（L0–L3：runtime_crash / runtime_crash / test_fail / test_fail）、`find_lookup`（L0–L3：test_fail / test_fail / test_fail / runtime_crash）。
  复核时杀死方式变了的有 0 个。
* **两个杀死方式的口径不等价**（生成区的交叉表）：目标的桩是 test_fail 的 640 个变异体里，有 97 个（15.2%）是崩溃 / 超时杀死的；目标的桩是崩溃 / 超时的 192 个变异体里，
  有 56 个（29.2%）记为 test_fail。所以报告给两张分层表：变异体怎么死的（`kill_mode`）和目标被零值桩杀死的方式（`stub_kill_mode`，测试有没有断言返回内容）。
* **提示词上下文被裁的题**：L0 的 208 道题里有 37 道（17.8%）有被裁掉的原型 / 宏 / 全局（按算子看，L0–L3 合计，DST 59 / 232、RVR 36 / 164、DGS 24 / 44 最多，见生成区「提示词上下文里因缺陷而多余的条目」），
  评审在第一轮的数据上数出的是 31 道；这一轮 L0 选中的变异体不同（洗牌种子变了），裁剪的判据也不同（可达性裁剪，宏体里的名字也算），数出来是 37 道。出题时这些条目不再进提示词，这样的题不进可比子集，报告里单列通过率。
* **耗时**：评审说「死循环要等满 `spec.timeout_s`（30–60 秒）是耗时的主要来源」不成立：9 个语料的 `timeout_s` 全是 30 秒（60 秒只是 mini 夹具的值）；kill 检查、复核和去注释验证的沙箱运行时间合计 5708.5 秒，
  其中 runtime_timeout 的运行 616.5 秒（10.8%），test_fail 的 3040.4 秒（53.3%），等价变异体和去注释的原函数（pass）1087.9 秒（19.1%）。
  NEG 取反循环条件会死循环这一点没错，超时型变异体只有 10 个，不过它们集中在少数语料：inih 4 个（沙箱时间 293.8 秒里有 246.0 秒是超时型运行）、mpc 2 个（沙箱时间 1772.6 秒里有 122.6 秒是超时型运行）、tinyexpr 4 个（沙箱时间 626.4 秒里有 247.9 秒是超时型运行），其余语料没有。inih（耗时 247.6 秒）、tinyexpr（耗时 258.9 秒）每级各有一个：四个级别依次处理（L1–L3 要等 L0 的位点），每级要等运行加复核各一个 `timeout_s`，耗时几乎全花在这上面。
* **NEG 的显眼程度随级别变化。** NEG 把条件改成 `!(c)`；L0 / L1 的代码里 `if (!(` 这种写法几乎不出现，L2 的 `if (c) A else B` → `if (!(c)) B else A` 让代码自带这种写法。
  复现办法：`grep -rh 'if (!(' tmp/obf/<语料>/<级别> --include=*.c --include=*.h | wc -l`（含测试文件；parson 的 L0 / L1 / L2 / L3 是 0 / 0 / 11 / 5，mpc 是 0 / 0 / 27 / 8，cJSON 自己的源码里就有 6 处）。
  L2 里条件被改写成 `!(c)` 的 NEG 位点本来就对不上 L0 的位点，不进可比子集；读按算子分层的表里 NEG 一行时仍要扣掉这一项。

### 10.3 回放复核（`check-mutants`）

用 `python3 -m bench check-mutants --jobs 6 --oracle` 把 mutate 选定的变异体当作候选在沙箱里再评测一遍（等价于用 `mock-unchanged` 评测，但不经过 generate / evaluate，也不写评测结果），
再把**去注释后的原函数**放回副本跑一遍（等价于 `mock-oracle`）。结果在生成区「回放复核」一节（`results/mutants-<语料>.check.json`）：

* 回放了 829 个变异体（3 道 L1–L3 的 `mpca_lang` 因为字面量里带着目标函数自己的原名，出题时作废，不在其中），全部仍在测试阶段失败（829 / 829），
  **没有一个回放通过测试**；去注释的原函数全部通过（829 / 829）。
* 杀死方式与 mutate 记下的相同的有 827 个，不同的 2 个（`mpcaf_grammar_string@L1`：runtime_timeout → test_fail、`mpcaf_grammar_string@L2`：runtime_timeout → test_fail）：同样是不终止并持续吃内存的目标，被超时杀掉还是被 OOM 杀掉取决于谁先到，两种结局都算被杀死，只影响分层标签。
* 这一步取代了第一轮文档里的「mock 验证」：那张表出自没有入库的一次性脚本（`tmp/real-repair-check`），别人没法复核；现在是仓库里的命令，e2e 和单元测试也覆盖它，随时可以重放。
  它不说明任何模型的能力，只验证出题的变异体确实稳定地让测试失败。

### 10.4 去注释与名字泄漏检查

* **为什么要去注释。** 符号混淆只改标识符，L1 以上函数体里的注释仍是项目原有的名字。生成区「函数体里的注释」给出：208 个目标里 50 个函数体有注释，其中 43 个的注释提到了会被 L1 改名的项目标识符
  （长度不小于 3 的词；这两个数以前是没有入库的一次性脚本算的，现在由 `experiment_record` 生成）。原样放进修复提示词会把本该隐藏的名字泄漏给模型，
  所以四个级别的变异体都先去注释（`mutate.strip_function_comments`）再做 kill 检查，提示词里放的就是 kill 检查验证过的那段文本。
* **去注释会不会改变行为。** 有注释的 200 个（目标, 级别）各把去注释后的**原函数**放回副本再跑一遍项目测试：200 次检查，0 次不通过。这一步现在放在搜索之前：不通过就不搜索，也不当 L1–L3 的参照。
* **泄漏检查**（生成区「修复提示词里的名字泄漏检查」）：L1–L3 的 624 个变异体里，字符串 / 字符常量之外没有任何被改名的原拼写（0 个）；
  字符串 / 字符常量里含这类拼写（长度不小于 3 的词）的有 36 个（cjson 12、mpc 24）。第一轮文档说这些「多半是 `null`、`file` 这类恰好也是项目标识符的英文词」，只有 cjson 的符合
  （`null`、`copy`、`test`、`path`、`value`）；mpc 的不符合，它们是库的领域词，出现在报错文字和语法名里（`"Invalid Regex Range Expression"`、`"Unknown Parser '%s'!"`、`"Invalid Grammar: %s"`、`"anchor"`、`"term"`）。
  按泄漏检查器的放行名单分开数：词全在放行名单里的 30 个（放行名单是常见英文词加上 mpc 的 spec 里写的 `anchor`、`ast`、`expr`、`grammar`、`regex`，
  所以 `Regex`、`Parser`、`Grammar` 这些领域词也在其中；放行只表示描述里出现它们不触发重试，不表示它们与领域无关），
  含放行名单之外的项目词（`stmt`、`mpca_lang`）的 6 个。字面量改了就改变行为，去不掉，这是修复任务名字隐藏程度的上限，写进了局限。
* **目标函数自己的原名出现在字面量里**的有 3 个（mpc 的 `mpca_lang`，L1–L3 各一道）：函数的新名字是 `f_<n>`，错误提示里却写着 `mpca_lang`，隐藏失败。
  这样的题现在出题时作废（`name_in_literal`），L0 的那道（名字本来就是真名）照常出题。
