# codegen-robustness-bench · 大模型代码生成鲁棒性评测平台 · 设计文档

版本 v0.1 · 2026-10-27 · 本文档是实现的接口契约：模块边界、函数签名、数据格式、验收标准都以此为准。实现者只能在不改变接口的前提下补充细节；要改接口先改本文档。

## 1. 问题与目标

现有代码生成评测（HumanEval、MBPP 以及直接取自 GitHub 的函数级基准）容易受训练数据泄漏影响：被测函数及其所在项目很可能出现在模型训练语料里，模型靠记忆而不是靠理解生成代码，分数无法反映真实的工程生成能力。

本平台从多个开源 C 项目中提取目标函数及其依赖上下文，对整个项目做三类可验证的代码混淆（符号、结构、语义），让模型在「同一份功能规格、不同混淆强度」下重新生成目标函数，把生成结果替换回项目、在沙箱里编译并运行项目自带测试，统计通过率的变化并对失败样本做错误归因。

要回答的问题：

1. 同一模型在无混淆（L0）与各级混淆（L1–L3）下的编译通过率、功能测试通过率相差多少；
2. 失败是哪一类（语法、依赖缺失、类型、逻辑、崩溃、超时），随混淆强度如何迁移；
3. 不同模型（deepseek-chat、deepseek-reasoner，以及任何 OpenAI 兼容端点）的横向对比；
4. L0 生成结果与原函数的相似度（记忆痕迹）是否在 L1 后明显下降。

不做的事：不评测多文件新增功能、不评测 C 以外的语言、不做模型微调。

## 2. 总体流程

```
prepare    克隆语料到 corpus/src/<name>，按 spec 校验构建与测试可用（沙箱内）
coverage   沙箱内以 --coverage 编译并跑测试，gcov 得到每个函数的执行次数
targets    选目标函数：非测试文件、非 main、语句数 ≥ 3、执行次数 > 0、stub-kill 通过
obfuscate  对整个项目生成 L1 / L2 / L3 三个混淆副本（含测试文件），记录映射与统计
verify     每个混淆副本的项目自带测试必须全部通过（oracle gate），否则该副本作废
describe   用 LLM 为每个目标函数生成「不含任何标识符」的功能规格（一次生成、四级共用）
generate   按 (target, level, model) 组织 prompt，调模型，缓存回复
evaluate   后处理 → 替换回混淆副本 → 沙箱编译 → 跑项目测试 → 记录
attribute  按 gcc JSON 诊断、退出信号、测试输出归因
report     汇总 model × level × corpus 的指标表、归因分布、相似度，输出 md / csv / 图
```

每一步幂等：输出已存在且输入哈希未变则跳过；所有随机性由 `--seed` 决定。

## 3. 语料

v1 用 9 个小型 C 开源库，全部有自带测试、纯 Makefile 或单条 gcc 命令即可构建，沙箱内已实测（2026-10-27，gcc:13 镜像）：

| 名称 | 构建与测试命令 | 规模 | 备注 |
|---|---|---|---|
| cJSON | `make test` | 2 个 .c | 测试在 test.c + tests/ |
| parson | `make test` | 362 用例 | |
| sds | `make sds-test && ./sds-test` | 46 用例 | 测试 main 由 -DSDS_TEST_MAIN 编进 sds.c |
| jsmn | `make test` | 多个二进制 | 头文件实现（jsmn.h），目标函数在头文件里 |
| tinyexpr | `make smoke && ./smoke` | 10118 断言 | |
| mpc | `make check` | 5.6 s | 最大的一个，6.3k 行 |
| tiny-regex-c | 只跑 tests/test1、tests/test2（随机测试依赖 python，不用） | | spec 里写显式 gcc 命令 |
| inih | `cd tests && bash unittest.sh` | 输出对比基线 | 要核实失败时的退出码或 diff 语义 |
| vec | `test/` 无 Makefile，spec 里写 gcc 命令 | | |

语料不提交进仓库，`prepare` 时按 spec 里的 url + commit 克隆到 `corpus/src/<name>`（克隆命令要绕开本机失效的代理：`git -c http.proxy= -c https.proxy= -c http.https://github.com/.proxy=`，并 `env -u http_proxy -u https_proxy -u all_proxy ...`）。

### 3.1 语料 spec（`corpus/specs/<name>.json`）

```json
{
  "name": "cjson",
  "url": "https://github.com/DaveGamble/cJSON.git",
  "commit": "<40 位，prepare 时若为空则写入 HEAD>",
  "license": "MIT",
  "project_files": ["cJSON.c", "cJSON.h", "cJSON_Utils.c", "cJSON_Utils.h", "test.c", "tests/*.c", "tests/*.h", "tests/unity/src/*.c", "tests/unity/src/*.h"],
  "target_files": ["cJSON.c", "cJSON_Utils.c"],
  "cflags": ["-std=c89", "-I.", "-DCJSON_EXPORT_SYMBOLS"],
  "build_cmd": "make test",
  "test_cmd": null,
  "pass_criteria": {"exit_code": 0},
  "coverage": {"env": {"CFLAGS": "--coverage -O0", "LDFLAGS": "--coverage"}, "gcda_glob": "**/*.gcda"},
  "timeout_s": 120,
  "notes": "..."
}
```

字段含义：`project_files` 是会被混淆、会被 libclang 解析的全部项目文件（含测试）；`target_files` 是允许选目标函数的文件；`cflags` 给 libclang 用（必须能把 target_files 解析到零致命错误）；`build_cmd` 跑完即含测试时 `test_cmd` 可为 null；`pass_criteria` 支持 `exit_code` 与可选 `stdout_regex`、`stdout_not_regex`；`coverage.env` 是注入到构建命令环境里的变量，若 Makefile 不吃 CFLAGS，spec 里改写 `coverage.build_cmd`。

## 4. 模块与接口

包名 `bench`，Python 3.10，依赖：标准库 + `clang==14.0`（`clang.cindex`，库文件 `/usr/lib/llvm-14/lib/libclang.so.1`，由 `bench/clangcfg.py` 统一设置）。HTTP 用标准库 `urllib`。不引入其它第三方依赖；测试用 pytest。

### 4.3 `bench/extract.py`

```python
@dataclass
class Dependencies:
    decls: list[str]        # 被调用的项目内函数的原型（去掉函数体）
    types: list[str]        # 用到的 struct / union / enum / typedef 完整定义，按依赖顺序
    globals: list[str]      # 用到的全局变量 extern 声明
    macros: list[str]       # 用到的项目内宏的完整 #define 行
    includes: list[str]     # 该文件里的系统头 #include 行
@dataclass
class FunctionTarget:
    target_id: str          # f"{corpus}:{file}:{name}"
    corpus: str; file: str; name: str
    signature: str          # 不含函数体的定义头，含存储类与返回类型
    start: int; end: int    # 整个定义在文件中的字节偏移 [start, end)
    body_start: int; body_end: int
    n_statements: int; n_lines: int
    callees: list[str]; deps: Dependencies
    doc_comment: str | None
def parse_file(spec, src_root, file) -> clang.cindex.TranslationUnit
def extract_functions(spec, src_root) -> list[FunctionTarget]
def locate(spec, src_root, name, file) -> FunctionTarget | None     # 混淆副本里按（映射后）名字重新定位
```

要求：只取有函数体的定义；排除 `main`、测试文件（不在 target_files 里的文件）、`static inline` 单语句函数；语句数按 `COMPOUND_STMT` 下直接子节点递归计数；依赖闭包只收项目文件内的声明（系统头里的一律不收，用 `includes` 带入）；对头文件实现的库（jsmn），目标函数在 .h 里也要能提取与替换。

### 4.4 `bench/coverage.py`

```python
def function_exec_counts(spec, src_root, sandbox) -> dict[str, int]   # key = f"{file}:{name}"
```

实现：工作副本里按 `spec.coverage` 注入 `--coverage` 构建并跑测试，然后在沙箱里对每个目标文件跑 `gcov -f -b -n <file>` 解析「Function '<name>' / Lines executed」或直接 `gcov -i`（JSON，gcc 13 支持 `--json-format`）取每个函数的 `execution_count`。

### 4.5 `bench/targets.py`

```python
@dataclass
class TargetFilter: min_statements=3; min_lines=4; max_lines=120; max_per_corpus=50; require_exec=True; require_stub_kill=True
def select_targets(spec, src_root, sandbox, flt: TargetFilter, seed: int) -> list[FunctionTarget]
def stub_kill(spec, src_root, target, sandbox) -> bool   # 用「返回零值 / 空函数体」桩替换目标函数，项目测试必须失败才算 True
```

stub 规则：返回类型 void → 空函数体；指针 → `return 0;`（或 NULL）；算术类型 → `return 0;`；结构体返回 → 零初始化变量后返回。stub 后测试仍通过的函数视为「测试覆盖不住」，不进入目标集，但计数写进报告。

### 4.6 `bench/obfuscate/`

```python
# __init__.py
LEVELS = ["L0", "L1", "L2", "L3"]      # L0 原样；L1 符号；L2 = L1 + 结构；L3 = L2 + 语义
@dataclass
class ObfResult: level: str; out_root: Path; rename_map: dict[str, str]; stats: dict
def obfuscate(spec, pristine_root, level, seed, out_root) -> ObfResult
# symbols.py
def collect_project_identifiers(spec, src_root) -> set[str]   # 项目文件内声明的函数、变量、参数、字段、类型、枚举常量、标签、宏 的拼写
def build_rename_map(names: set[str], seed) -> dict[str, str]  # 双射；函数 f_<n>、类型 t_<n>、变量 v_<n>、宏 M_<n>、字段 m_<n>，n 由 seed 打乱
def apply_renames(spec, src_root, mapping) -> dict             # 逐文件 token 级替换：只替换 IDENTIFIER token，不碰字符串字面量与注释；返回每文件替换计数
# structure.py
def transform_structure(spec, src_root, seed) -> dict          # 返回每类变换的应用次数
# semantic.py
def transform_semantic(spec, src_root, seed) -> dict
# verify.py
@dataclass
class VerifyResult: ok: bool; build_rc: int; stdout_tail: str; relocated: int; missing: list[str]
def verify(spec, obf_root, targets, mapping, sandbox) -> VerifyResult   # 项目测试全过 + 每个目标函数能按映射名重新定位
```

符号混淆（L1）规则：

- 收集范围 = 在 `project_files` 内声明的所有实体拼写；排除：`main`、C 关键字、系统头里出现过的拼写（任一系统头声明过同名实体即排除，避免改坏 libc 调用）、以 `__` 开头的拼写、`project_files` 外（如 unity 框架）的拼写——unity 等第三方测试框架目录在 spec 里用 `"vendored": [...]` 标出，解析但不改名。
- 替换是 token 级、按拼写的双射（同一拼写全项目映射到同一新名），`#define` 行、`#ifdef` 行里的标识符一并替换；字符串字面量不替换，所以 `#x` 字符串化会改变输出，碰到这种宏（宏体含 `#` 或 `##`）就把相关拼写加入排除集并记录。
- 新名字不能和任何保留拼写、系统头拼写冲突；生成后用 libclang 重新解析，诊断里出现 error 即判失败。
- 保留 `include` 路径、文件名不变（文件名不改，避免 Makefile 失效）。

结构混淆（L2，在 L1 之上，作用于目标文件与其它项目文件的函数体）：

1. `for (init; cond; step) body` → `{ init; while (cond) { body step; } }`，仅当 body 内无 `continue`；
2. `if (c) A else B` → `if (!(c)) B else A`；
3. `x op= e` → `x = x op (e)`，仅当 x 是单一标识符或 `a->b` / `a.b` 形式；
4. `return c ? a : b;` → `if (c) return a; else return b;`；
5. 把同一声明语句里的多个声明拆成多条（`int a = 1, b;` → `int a = 1; int b;`）。
   每条变换在 AST 节点上做、按 token 范围改源码、从后往前应用避免偏移失效；每个函数体内按 seed 随机选用其中约 50% 的可用位置。变换后必须能用 libclang 零 error 重新解析。

语义混淆（L3，在 L2 之上，表达式级等价改写）：

1. `a < b` → `b > a`、`a <= b` → `b >= a`（操作数无副作用：标识符、字面量、成员访问）；
2. `!(a && b)` → `(!a || !b)`、`!(a || b)` → `(!a && !b)`；
3. `x == 0` 与 `!x` 互换（x 为整型表达式，类型由 libclang 判定）；
4. `a + b` / `a * b` 交换律换序（操作数无副作用、非指针运算）；
5. 在函数体开头插入对输入无影响的 opaque 语句：`{ volatile int _k = 0; (void)_k; }`，变量名也经过改名表。
   同样要求零 error 重新解析，且 verify 必须通过。

### 4.7 `bench/llm.py`

```python
@dataclass
class Reply: text: str; model: str; prompt_tokens: int; completion_tokens: int; cached: bool; latency_s: float; raw: dict
class LLM:  # 抽象
    def chat(self, messages: list[dict], temperature=0.0, max_tokens=4096, seed: int | None = None) -> Reply
class OpenAICompat(LLM):   # base_url, api_key(环境变量名), model；重试 5 次指数退避；429/5xx 重试；超时 120 s
class MockLLM(LLM):        # mode: "oracle"（返回被测目标在该混淆级下的原函数体）| "broken"（返回带语法错误的函数）| "wrong"（返回编译通过但逻辑错误的函数）| "empty"
class Cache:               # results/cache/<sha256(model, messages, temperature, max_tokens)>.json
```

API key 只从环境变量读（`DEEPSEEK_API_KEY`、`OPENAI_API_KEY` 等，spec 里写变量名），绝不写进代码、日志或结果文件；每次调用的 usage 写进 `results/usage.jsonl`。

### 4.8 `bench/describe.py`

```python
def describe(target: FunctionTarget, code: str, llm: LLM, project_names: set[str]) -> str
def leaks(description: str, project_names: set[str]) -> list[str]   # 描述里出现的项目标识符
```

规格要求：用英文写；只描述行为契约（参数按位置称呼「the first argument」，返回值、边界条件、错误处理、副作用、对输入的假设）；不得出现任何项目内标识符、不得引用代码；长度 80–250 词。生成后用 `leaks` 检查，泄漏则带着泄漏清单重新生成，最多 3 次，仍泄漏则该目标标记 `describe_failed` 并排除。描述由最强可用模型生成一次，缓存，四级共用。

### 4.11 `bench/runner.py`

```python
@dataclass
class EvalResult: task_id, model, sample_idx, stage: str, rc: int, timed_out: bool, signal: int | None, diagnostics: list[dict], test_stdout_tail: str, duration_s: float
```

编译诊断：在 `build_cmd` 前注入 `CFLAGS="$CFLAGS -fdiagnostics-format=json"`（spec 不吃 CFLAGS 的，先单独对目标文件跑一次 `gcc -fsyntax-only -fdiagnostics-format=json`，再跑正式构建）。stage 取值：`syntax`（单文件语法检查失败）/ `build`（整体构建失败）/ `test`（测试失败）/ `pass`。

### 4.12 `bench/attribute.py`

```python
CATEGORIES = ["pass", "extract_fail", "compile_syntax", "compile_undeclared", "compile_type", "compile_other", "link_error", "runtime_crash", "runtime_timeout", "test_fail"]
def attribute(ev: EvalResult, cand: Candidate) -> tuple[str, str]   # (category, detail)
```

规则：无代码块 → extract_fail；诊断 message 含 `expected`/`syntax`/`stray` → compile_syntax；含 `undeclared`/`implicit declaration`/`unknown type`/`has no member` → compile_undeclared；含 `incompatible`/`too few`/`too many`/`makes pointer`/`invalid operands` → compile_type；其它编译错误 → compile_other；构建输出含 `undefined reference` → link_error；测试阶段 signal 在 {SIGSEGV, SIGABRT, SIGFPE, SIGBUS} → runtime_crash；timed_out → runtime_timeout；测试阶段 rc≠0 → test_fail。一个样本只归一类，按上述顺序取第一个命中。

### 4.13 `bench/similarity.py`

```python
def normalized_similarity(a: str, b: str) -> float   # 标识符归一化（全部换成 ID）、去空白后的 difflib ratio
```

用于 L0/L1 生成结果与（对应混淆级的）原函数体之间的相似度，作为记忆痕迹指标。

### 4.14 `bench/metrics.py` 与 `bench/report.py`

按 model × level × corpus 汇总：n、compile_rate（stage ≥ test）、pass_rate、每类归因占比、平均相似度、token 用量；另给 model × level 的总表与「相对 L0 的下降」。输出 `results/summary-<tag>.md`、`.csv`，图用 matplotlib 存 `results/fig-<tag>.png`（可选）。

### 4.15 `bench/cli.py`

`python3 -m bench <cmd>`：`prepare` / `coverage` / `targets` / `obfuscate --level` / `verify` / `describe --model` / `generate --model --levels --samples` / `evaluate` / `report --tag`，以及 `e2e --backend mock` 一键跑通全链路（oracle 模式必须 100% pass，broken 模式必须 100% compile_syntax，wrong 模式必须 100% test_fail）。所有命令接受 `--corpus`（可多选）、`--seed`、`--jobs`。

## 5. 数据文件（全部 JSONL，追加写，含 `schema_version`）

- `results/targets-<corpus>.jsonl`：FunctionTarget 全字段 + `exec_count` + `stub_killed`
- `results/obf-<corpus>-<level>.json`：rename_map、stats、verify 结果、源码树哈希
- `results/descriptions.jsonl`：target_id、description、model、leak_retries
- `results/tasks.jsonl`：Task 全字段
- `results/generations-<model>.jsonl`：task_id、sample_idx、reply 文本、usage、cached、latency
- `results/results-<tag>.jsonl`：EvalResult + category + detail + similarity
- `results/usage.jsonl`：每次 API 调用的 token 用量

## 6. 可信度措施（必须实现，不可裁掉）

1. oracle gate：每个混淆副本先用原函数体（混淆后）走一遍完整 evaluate，必须 pass；不过的副本或目标作废并计数。
2. stub-kill：目标函数被桩替换后项目测试必须失败，否则不入选。
3. MockLLM 三种模式的 e2e 自测固化在 `tests/test_e2e_mock.py`，CI 级别必须绿。
4. 描述泄漏检查：描述里不得出现任何项目标识符（含 L0 的真名）。
5. 全链路确定性：seed 固定则目标集、改名表、变换位置、prompt 完全一致；LLM 调用 temperature=0 并带缓存。
6. 结果文件自带输入哈希（源码树、spec、prompt 模板版本），report 时校验。
7. README 的「局限」一节如实写：功能规格由 LLM 生成（规格歧义会抬高失败率，报告 L0 通过率作上限参考）、语料是知名小库（L0 可能已被记忆，这正是对照的意义）、只测 C、单函数粒度、测试强度依赖各库自带测试（stub-kill 只保证非空）、结构与语义变换覆盖的语法子集有限。

## 7. 测试要求（pytest，`tests/`）

- `test_extract.py`：对 `tests/fixtures/mini/` 里的小项目（自写，含 struct、宏、全局、两个 .c 一个 .h、Makefile 和测试）提取函数、依赖闭包、字节偏移往返（替换回去后文件不变）。

- `test_structure.py` / `test_semantic.py`：每条变换的最小用例 + mini 项目变换后测试仍通过。
- `test_postprocess.py`、`test_attribute.py`：各类回复与诊断的归类。
- `test_e2e_mock.py`：mini 项目全链路三种 MockLLM 模式。
- 真实语料的 `prepare / coverage / targets / obfuscate / verify` 结果作为集成检查写进 `docs/实验记录.md`，不进单测。
