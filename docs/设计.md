## 1. 问题与目标

现有代码生成评测（HumanEval、MBPP 以及直接取自 GitHub 的函数级基准）容易受训练数据泄漏影响：被测函数及其所在项目很可能出现在模型训练语料里，模型靠记忆而不是靠理解生成代码，分数无法反映真实的工程生成能力。

本平台从多个开源 C 项目中提取目标函数及其依赖上下文，对整个项目做三类可验证的代码混淆（符号、结构、语义），让模型在「同一份功能规格、不同混淆强度」下重新生成目标函数，把生成结果替换回项目、在沙箱里编译并运行项目自带测试，统计通过率的变化并对失败样本做错误归因。

要回答的问题：

1. 同一模型在无混淆（L0）与各级混淆（L1–L3）下的编译通过率、功能测试通过率相差多少；
2. 失败是哪一类（语法、依赖缺失、类型、逻辑、崩溃、超时、违反约束），随混淆强度如何迁移；
3. 不同模型的横向对比：DeepSeek 现行模型（`deepseek-flash`、`deepseek-v4-pro` 及其思考版本，见 4.7）和任何 OpenAI 兼容端点。
   v0.1 写的 `deepseek-chat` / `deepseek-reasoner` 在官方 Change Log 里有弃用通知，只作为 legacy 预设保留；
4. L0 生成结果与原函数的相似度（记忆痕迹）是否在 L1 后明显下降。

不做的事：不评测多文件新增功能、不评测 C 以外的语言、不做模型微调。

关于问题 1 和 2 的适用范围：L2、L3 只改函数体，而提示词里没有函数体（见 4.9），所以 L1、L2、L3 的提示词逐字相同，
这三级回答的是「同一份回复放回不同混淆程度的项目后还能不能编过、测过」；能反映模型行为差异的只有 L0 对 L1。
这一点写在 README 局限、报告的局限一节和报告表格下方的固定提示里（见 4.14）。

## 2. 总体流程

```
prepare    取语料到 corpus/src/<name>（复制本地镜像或克隆），按 spec 校验构建与测试可用（沙箱内）
coverage   沙箱内以 --coverage 编译并跑测试，gcov 得到每个函数的执行次数
targets    选目标函数：非测试文件、非 main、语句数 ≥ 3、执行次数 > 0、stub-kill 通过
obfuscate  对整个项目生成 L0 / L1 / L2 / L3 四个副本（含测试文件），记录映射与统计，并 verify
verify     oracle gate：每个副本的项目自带测试必须全部通过；再用混淆后的原函数文本逐目标走一遍完整 evaluate，必须通过，否则该目标作废
mutate     （缺陷修复任务，见附录）在每个副本的目标函数里注入一个能被项目测试捕获的缺陷，沙箱里 kill 检查通过（判为杀死的复核一次）才出题；
           L1–L3 先试 L0 选定的位点在本级的对应位点，尽量四级是同一个缺陷
check-mutants  （缺陷修复任务）把 mutate 选定的变异体在沙箱里回放复核，都要稳定地让项目测试失败
describe   用 LLM 为每个目标函数生成「不含任何标识符」的功能规格（一次生成、四级共用）
generate   按 (target, level, model, sample) 组织 prompt，调模型，缓存回复；调用失败的样本单独落盘（`--task repair` 处理缺陷修复任务）
evaluate   后处理 → 硬性约束检查 → 替换回混淆副本 → 沙箱编译 → 跑项目测试 → 归因 → 相似度，并写完整性记录（`--task repair` 同）
report     汇总 model × level × corpus 的指标表、归因分布、相似度，输出 md / csv / 图（生成任务与缺陷修复任务并列）
```

每一步幂等：输出已存在且输入哈希未变则跳过；所有随机性由 `--seed` 决定。
出题（`generate`、`evaluate` 的前置）时会重新核对上游产出：oracle gate 对应的目标集 / 副本、功能规格的输入哈希与泄漏检查、
stub-kill 记录，对不上的目标作废并计数，不会因为中间某个阶段被跳过就用上过期数据（见 6.8）。

## 3. 语料

v1 用 9 个小型 C 开源库，全部有自带测试、纯 Makefile 或单条 gcc 命令即可构建，沙箱内已实测（2026-10-27，gcc:13 镜像）：

| 名称 | 上游的构建与测试方式（spec 里是等价的显式命令，一律引用 `$CFLAGS` / `$LDFLAGS`） | 规模 | 备注 |
|---|---|---|---|
| cJSON | 显式 gcc 命令逐个编译运行 tests/ 下的 Unity 用例，再编 test.c | 21 个测试文件 | 不走 `make test`：它只编 cJSON.c + test.c 且带 -Werror，cJSON_Utils.c 不参与 |
| parson | `make test` | 362 用例 | |
| sds | `make sds-test && ./sds-test` | 46 用例 | 测试 main 由 -DSDS_TEST_MAIN 编进 sds.c，所以 `sdsTest` 要用 `exclude_targets` 排除 |
| jsmn | `make test` | 多个二进制 | 头文件实现（jsmn.h），目标函数在头文件里 |
| tinyexpr | `make smoke && ./smoke` | 10118 断言 | |
| mpc | `make check` | 5.6 s | 最大的一个，6.3k 行 |
| tiny-regex-c | 只跑 tests/test1、tests/test_compile（随机测试依赖 python，不用） | | spec 里写显式 gcc 命令 |
| inih | `cd tests && bash unittest.sh` | 输出对比基线 | |
| vec | `test/` 无 Makefile，spec 里写 gcc 命令 | | |

各语料的 spec 是构建 / 测试命令的准确来源，上表只是概览。

语料不提交进仓库，`prepare` 把它放到 `corpus/src/<name>`，来源按顺序有两种：

1. 本地镜像：**只有**设置了环境变量 `CORPUS_MIRROR` 才会用，它指向的目录里按仓库名放着 git 克隆；存在就直接复制，不联网；
   没设置就不会去猜任何本机目录；
2. 按 spec 里的 url + commit 克隆。联网命令默认 180 s 超时（`CORPUS_GIT_TIMEOUT`）。环境变量里配了代理时，先探测它连不连得上：
   连得上照常用，一个都连不上才临时清掉代理变量并给 git 加 `-c http.proxy=` 等参数绕开，免得 clone 卡满超时；
   `CORPUS_KEEP_PROXY=1` 强制保留，`CORPUS_NO_PROXY=1` 强制清掉。调模型的客户端默认走环境变量里的代理，`BENCH_LLM_NO_PROXY=1` 关掉。

git 命令一律带 `-c core.hooksPath=/dev/null`：语料仓库里即使带了 hook 脚本，也不会在宿主机上执行。

### 3.1 语料 spec（`corpus/specs/<name>.json`）

```json
{
  "name": "cjson",
  "url": "https://github.com/DaveGamble/cJSON.git",
  "commit": "<40 位，prepare 时若为空则写入 HEAD>",
  "license": "MIT",
  "project_files": ["cJSON.c", "cJSON.h", "cJSON_Utils.c", "cJSON_Utils.h", "test.c", "tests/*.c", "tests/*.h", "tests/unity/src/*.c", "tests/unity/src/*.h"],
  "target_files": ["cJSON.c", "cJSON_Utils.c"],
  "cflags": ["-std=c89"],
  "build_cmd": "<显式 gcc 命令，一律引用 $CFLAGS / $LDFLAGS>",
  "test_cmd": null,
  "pass_criteria": {"exit_code": 0},
  "coverage": {"env": {"CFLAGS": "--coverage -O0", "LDFLAGS": "--coverage"}},
  "timeout_s": 30,
  "notes": "...",
  "vendored": ["tests/unity"],
  "keep_names": [],
  "exclude_targets": [],
  "allow_words": ["codepoint"]
}
```

字段含义：`project_files` 是会被混淆、会被 libclang 解析的全部项目文件（含测试）；`target_files` 是允许选目标函数的文件；
`cflags` 给 libclang 和单文件语法检查用（必须能把 target_files 解析到零致命错误）；`build_cmd` 跑完即含测试时 `test_cmd` 可为 null；
`coverage.env` 是注入到构建命令环境里的变量，若 Makefile 不吃 CFLAGS，spec 里改写 `coverage.build_cmd`（`gcda_glob` 在 v0.1 的字段表里，
但没有任何代码读它，v0.2 删掉，写了会校验报错）。

`pass_criteria` 支持 `exit_code` 与可选 `stdout_regex`、`stdout_not_regex`（对 stdout 按多行模式搜索）。沙箱把超过 64 KB 的输出从中间截断，
靠输出文字做的判据落在被丢弃的部分就会漏判，所以输出被截断时 `CorpusSpec.judge` 一律不认通过（返回「因截断而拒绝」标记）。

**每个语料的判据都必须挡得住候选里提前 `exit(0)`**：只看退出码的语料，候选写一句 `exit(0);` 程序就以 0 退出。
所以 spec 要求测试输出里出现完成标志（cJSON 每个 Unity 可执行文件的 `N Tests 0 Failures M Ignored` 汇总行、jsmn 四次运行各自的 `FAILED: 0`、
sds / vec / mpc / tiny-regex-c 的汇总行、parson 两次运行各自的 `Tests failed: 0`、tinyexpr 的 `ALL TESTS PASSED`，inih 则对输出做基线 diff；
必要时限定出现次数。检查可以写在 `build_cmd` 里，缺了就让构建命令非零退出，也可以写进 `stdout_regex`）。
`tests/test_corpus.py` 对 9 个语料各做一个「提前 exit(0)」的变异，要求都判失败。

四个可选字段（v0.1 字段表之外）：

* `vendored`：第三方代码目录（相对项目根，如 cJSON 的 `tests/unity`）。这些文件仍在 `project_files` 里、会被 libclang 解析，但符号混淆不改它们的名字（4.6）；
* `keep_names`：必须保持原拼写的名字，主要是只在构建命令里用 `-DNAME` 传入、源码里又有 `#define NAME` 默认值的配置宏（inih 的 `INI_MAX_LINE` 一类）；
* `exclude_targets`：不能当目标函数的名字（`name` 或 `file:name`）。典型是编进目标文件的测试驱动（sds 的 `sdsTest`）：把它换成桩，
  测试程序的汇总行就没了，会被误判成「桩被杀死」（4.5）；
* `allow_words`：描述的泄漏检查里，除通用英文词表外额外放行的词，只用于这个语料里确实是领域通用词、又恰好是项目标识符的少数几个（4.8）。

`CorpusSpec.digest()` 只覆盖影响构建与测试语义的字段，`url`、`license`、`notes`、`allow_words` 不参与：给 notes 补一句备注不该让整套产出作废。
构建命令里不带 `-Werror` / `-pedantic-errors`：L2 / L3 变换和模型生成的代码都可能引入新警告，把警告当错误会让失败原因和被测能力无关。

## 4. 模块与接口

包名 `bench`，Python ≥ 3.10（`bench/__init__.py` 在 import 时检查版本），依赖：标准库 + `clang==14.0`（`clang.cindex`，库文件默认 `/usr/lib/llvm-14/lib/libclang.so.1`，
环境变量 `LIBCLANG_PATH` 可覆盖）。HTTP 用标准库 `urllib`。不引入其它第三方依赖；测试用 pytest，静态检查用 pyflakes。
所有 libclang 配置和解析参数的唯一出口是 `bench/clangcfg.py`（4.16）。除 `bench/__init__.py` 外，包内一律用绝对导入（`from bench.xxx import ...`）。

### 4.2 `bench/sandbox.py`

```python
@dataclass
class RunResult: rc: int; stdout: str; stderr: str; duration_s: float; timed_out: bool; signal: int | None
                 io_error: str = ""; stdout_truncated: bool = False; stderr_truncated: bool = False
class DockerSandbox:
    def __init__(self, image="gcc:13", cpus=1.0, memory="1g", pids=256, timeout_s=120, uid=None, gid=None)
    def run(self, workdir: Path, cmd: str, env: dict | None = None, timeout_s: int | None = None) -> RunResult
    def image_id(self) -> str; def identity(self) -> dict      # 镜像标签 + 镜像 ID + 资源上限，进输入哈希与结果记录
    @staticmethod
    def docker_available(image=None) -> bool
class SandboxError(RuntimeError)                              # docker 本身出错（镜像缺失、守护进程不可用、读输出管道失败），不是样本失败
```

固定参数：`docker run --rm --name <唯一名> --network none --cpus --memory --memory-swap <同 memory> --pids-limit --security-opt no-new-privileges
--cap-drop ALL --ulimit core=0 -u uid:gid -e HOME=/tmp -v <workdir>:/work -w /work <image> bash -c "timeout -s KILL <timeout> bash -c '<cmd>'"`。
超时必须罩住整条命令（cmd 里可能有 `a && b; c` 这样的复合语句），所以是 `timeout` 包 `bash -c`，不是 v0.1 写的反过来。
`--memory-swap`（禁用 swap，超限直接 OOM）、`--ulimit core=0`（不产生 core 文件）、`--name`（超时或被中断时按名字强杀，不留孤儿容器）只收紧、不放宽。
超时判定：rc=124（`timeout` 自己的）一律记超时；rc=137 既可能是超时也可能是 OOM 或程序自己 kill -9，只有总耗时不少于 timeout 才记超时。
信号从 rc 换算（128+n，n 在 1..64）。stdout / stderr 各截断到 64 KB（保留首尾，中间插入提示），截断标记写进 `RunResult`。
读输出管道出错记 `io_error`，调用方用 `raise_if_docker_failed` 转成 `SandboxError`，不能当作样本失败。
模型生成的代码只允许在这个沙箱里编译和执行。

### 4.3 `bench/extract.py`

```python
@dataclass
class Dependencies:
    decls: list[str]        # 被调用的项目内函数的原型（去掉函数体）
    types: list[str]        # 用到的 struct / union / enum / typedef 完整定义，按依赖顺序
    globals: list[str]      # 用到的全局变量 extern 声明
    macros: list[str]       # 用到的项目内宏的完整 #define 行
    includes: list[str]     # 该文件里的系统头 #include 行
@dataclass
class FunctionTarget:
    target_id: str          # f"{corpus}:{file}:{name}"
    corpus: str; file: str; name: str
    signature: str          # 不含函数体的定义头，含存储类与返回类型
    start: int; end: int    # 整个定义在文件中的字节偏移 [start, end)
    body_start: int; body_end: int
    n_statements: int; n_lines: int
    callees: list[str]; deps: Dependencies
    doc_comment: str | None
def parse_file(spec, src_root, file) -> clang.cindex.TranslationUnit
def extract_file(spec, src_root, file) -> list[FunctionTarget]          # 单个文件里全部有函数体的定义，不做 main / static inline 的排除
def extract_functions(spec, src_root) -> list[FunctionTarget]
def locate(spec, src_root, name, file) -> FunctionTarget | None         # 混淆副本里按（映射后）名字重新定位
```

要求：只取有函数体的定义；排除 `main`、测试文件（不在 target_files 里的文件）、`static inline` 且语句数 ≤ 1 的函数；由宏生成、无法按字节偏移替换的函数定义跳过（日志里记数）；
语句数按 `COMPOUND_STMT` 下直接子节点递归计数；依赖闭包只收项目文件内的声明（系统头里的一律不收，用 `includes` 带入）；
对头文件实现的库（jsmn），目标函数在 .h 里也要能提取与替换。所有偏移都是字节偏移，文件一律按 bytes 读写。

### 4.4 `bench/coverage.py`

```python
def function_exec_counts(spec, src_root, sandbox, *, work_root=None, keep_workdir=False, stats=None) -> dict[str, int]   # key = f"{file}:{name}"
```

实现：工作副本里按 `spec.coverage` 注入 `--coverage` 构建并跑测试，然后在沙箱里对每个 `.gcda` 单独跑 `gcov --json-format <绝对路径>`（不按源文件名加 `-o`：
一条 gcc 命令同时编译多个源文件时数据文件名对不上），宿主机读 `*.gcov.json.gz`，把落在目标文件里的函数的 `execution_count` 按 `<文件>:<函数名>` 累加。
`.gcda` 一律用 `find -name '*.gcda'` 全量收集（v0.1 的 `gcda_glob` 字段删除）。个别 `.gcda` 的 gcov 失败只记 warning，失败原因（`gcov.err` 的尾部）写进 `stats["failed"]`，
全部失败才抛 `CoverageError`。根本没被编译进任何测试程序的函数不在字典里，调用方按 0 处理。

### 4.5 `bench/targets.py`

```python
@dataclass
class TargetFilter: min_statements=3; min_lines=4; max_lines=120; max_per_corpus=50; require_exec=True; require_stub_kill=True
def select_targets(spec, src_root, sandbox, flt, seed, *, jobs=1, scan_all=False, stats=None, work_root=None) -> list[FunctionTarget]

```

过滤顺序与排除原因：`spec_excluded`（`exclude_targets`）、`few_statements`、`too_short` / `too_long`、`not_executed`、`stub_survived`、`stub_build_error`、
`stub_unsupported`、`not_sampled`。抽样按 `sha256(f"{seed}|{target_id}")` 排序，再按这个顺序逐个做 stub-kill，凑够 `max_per_corpus` 个被杀死的函数为止；
排序键只和 seed、target_id 有关，同一个 seed 在任何机器、任何并发度下选出同一批目标。`scan_all=True` 让所有候选都做 stub-kill
（入选目标与默认模式完全相同，多花几分钟），为的是得到整个语料「测试覆盖不住的函数」的完整数字写进报告。入选前先在未改动的副本上跑一次基线，基线不过就停。

stub 规则：返回类型 void → `{ }`；指针或算术类型（含 enum、_Bool、浮点）→ `{ return 0; }`；struct / union / complex →
`{ static T _bench_zero; return _bench_zero; }`（静态存储期天然零初始化，不依赖 `memset`）。只替换函数体，函数头保持原文。
stub 后测试仍通过的函数视为「测试覆盖不住」，不进入目标集，但计数写进报告；桩没编过单独记 `stub_build_error`，不会被当成杀死。

**杀死方式**（v0.2 新增）：测试阶段失败都算被杀死，但方式不同，逐目标记在 `targets-<corpus>.jsonl` 的 `stub_kill_mode`：
`test_fail`（断言失败）、`runtime_crash`（桩让测试程序崩溃：SIGSEGV / SIGABRT / SIGFPE / SIGBUS）、`runtime_timeout`（桩让测试超时）。
后两种目标的测试并没有断言函数返回了什么，任何不崩溃的错误实现都能通过，通过率会被高估。v0.2 没有再加「非零桩」把它们剔掉，
而是把杀死方式带进 Task 和结果行，报告按杀死方式分层给出通过率（4.14），README 局限里写明。
`--no-stub-kill` 必须同时加 `--unsafe-debug`，产出的目标 `stub_killed` 为 None，出题时按 `stub_unchecked` 作废（`--unsafe-debug` 才放行），报告开头写明。

符号混淆（L1）规则：

- 收集范围 = 在 `project_files` 内声明的所有实体拼写；解析按两套参数各走一遍：`spec.cflags`，以及再加上构建命令里出现过的全部 `-D` 的「并集配置」
  （这样 `#ifdef JSMN_PARENT_LINKS` 之类条件编译块里的声明也看得见）。
- 排除（绝不改名）：`main`、C 关键字、以 `__` 或 `_大写` 开头的保留拼写；系统头里声明过的拼写（只看文件作用域名字和成员）；`project_files` 外和 `vendored` 里的拼写，
  以及被 vendored 代码引用的项目实体；以隐式声明方式调用的 libc 函数；项目里只有声明、没有定义的符号；构建命令里用 `-D` / `-U` 指定的宏和 `keep_names`；
  `#pragma` 行里的拼写。
- 替换是 token 级、按拼写的双射（同一拼写全项目映射到同一新名），`#define` 行、`#ifdef` 行里的标识符一并替换；字符串字面量和注释不替换，不碰 `#include` 里的头文件名。
- **字符串化宏**：宏体含 `#` 或 `##` 的宏所涉及的拼写（宏名、形参、宏体里的标识符）加入排除集；`##` 宏的调用实参、由 `##` 拼出来的名字一并排除。
  `#` 宏（字符串化）的调用实参分两种：`target_files`（库自己的源码）里的一律排除，因为被字符串化的名字会成为库运行时输出的一部分；
  测试文件里的默认照常改名（否则大量 `CHECK(f(x) == 1)` 这样的断言会让所有被调函数都改不了），改了名的个数如实记在 `stats["stringified_names_renamed"]`
  并写进报告的「混淆副本」表；`strict_stringify=True` 则连同测试文件里的一起排除（输出文字完全不变，代价是排除数大幅上升）。
  默认（`auto`）先用非 strict，verify 不过且确有名字出现在 `#` 宏的调用实参里就退回 strict 重做，每次尝试记进 `stats["attempts"]`。
  这是对 v0.1 「宏体含 # 或 ## 就把相关拼写加入排除集」的细化，原因和风险见第 10 节。
- 新名字不能和任何保留拼写、系统头拼写冲突。改名后重新解析每个 target_file（两套配置），error 数不得比改名前多（改名前为 0 就必须仍为 0），否则抛 `RenameError`
  并恢复所有文件（v0.1 写的是「出现 error 即失败」，语料自带的头在个别配置下本来就有 error，所以口径改成不得变多）。
- 保留 `include` 路径、文件名不变（文件名不改，避免 Makefile 失效）。

结构混淆（L2，在 L1 之上，作用于目标文件与其它项目文件的函数体，`vendored` 除外，测试文件照改）：

1. `for (init; cond; step) body` → `{ init; while (cond) { body step; } }`，仅当 body 内无 `continue`；
2. `if (c) A else B` → `if (!(c)) B else A`；
3. `x op= e` → `x = x op (e)`，仅当 x 是单一标识符或 `a->b` / `a.b` 形式，且 e 里没有函数调用；
4. `return c ? a : b;` → `if (c) return a; else return b;`（要求分支类型与整个三目一致，避免通常算术转换改变返回值）；
5. 把同一声明语句里的多个声明拆成多条（`int a = 1, b;` → `int a = 1; int b;`）。
   每条变换在 AST 节点上做、按字节区间渲染（嵌套的位置同时生效）；每个函数体内按 seed 随机选用其中约 50% 的可用位置。
   宏生成的语句、宏参数里的位置、被 `#if` 劈开的位置一律不动。变换后必须能用 libclang 零 error 重新解析，有 error 时二分回滚只撤销出错的位置。

语义混淆（L3，在 L2 之上，表达式级等价改写）：

1. `a < b` → `b > a`、`a <= b` → `b >= a`（操作数无副作用：标识符、字面量、成员访问，算术类型）；
2. `!(a && b)` → `(!a || !b)`、`!(a || b)` → `(!a && !b)`；
3. `x == 0` 与 `!x` 互换（x 为整型表达式，类型由 libclang 判定）；
4. `a + b` / `a * b` 交换律换序（操作数无副作用、非指针运算）；
5. 在函数体开头插入对输入无影响的 opaque 语句：`{ volatile int v_<n> = 0; (void)v_<n>; }`，变量名走与 L1 同一张改名表的取名规则（`build_rename_map`，种类按变量），
   不是固定模式。
   同样要求零 error 重新解析，且 verify 必须通过。

- 精确匹配：把描述切成标识符记号，区分大小写地与项目标识符集合比对；

编译诊断：在 `build_cmd` 前注入 `CFLAGS="$CFLAGS -fdiagnostics-format=json"`，同时先对目标文件单独跑一次 `gcc -x c -fsyntax-only -fdiagnostics-format=json`
（只带 `spec.cflags` 里能直接给 gcc 的部分）。stage 取值：`extract`（抽不出代码）/ `policy`（违反硬性约束，没进沙箱）/ `syntax`（单文件语法检查失败）/
`build`（整体构建失败）/ `test`（测试失败）/ `pass`。

测试含在 `build_cmd` 里时（九个语料都是这样），一次沙箱运行里分不清构建失败和测试失败，按证据判：输出里有 gcc 的 error 级诊断、链接错误或编译器 / 链接器 / make 的报错行记 `build`，
否则记 `test`；**超时且没有任何输出证据时按构建阶段超时处理**（记 `build`，不计入编译通过率，也不算 stub-kill 的杀死），免得把「编译阶段超时」算成「编译通过」。
输出被截断（`stdout_truncated`）时输出型判据一律不认通过。

### 4.12 `bench/attribute.py`

```python
CATEGORIES = ["pass", "extract_fail", "policy_violation", "compile_syntax", "compile_undeclared", "compile_type", "compile_other",
              "link_error", "runtime_crash", "runtime_timeout", "test_fail"]       # 定义在 bench/vocab.py
def attribute(ev: EvalResult | None, cand: Candidate) -> tuple[str, str]   # (category, detail)；detail 是给人看的英文短句，会混着 gcc 原文
```

规则（一个样本只归一类，按下列顺序取第一个命中）：无代码块 → `extract_fail`；违反硬性约束 → `policy_violation`；阶段 pass → `pass`；
诊断 message 含 `expected`（但 `was expected` 除外）/`syntax`/`stray`/`unterminated`/`missing terminating` → `compile_syntax`；
含 `undeclared`/`implicit declaration`/`unknown type`/`has no member` → `compile_undeclared`；含 `incompatible`/`too few`/`too many`/`makes pointer`/`invalid operands` → `compile_type`；
其它编译错误 → `compile_other`；构建输出含 `undefined reference` 等链接错误 → `link_error`（被隐式声明的函数在 gcc 13 里是 warning，到链接才死，归 `compile_undeclared`）；
测试阶段 signal 在 {SIGSEGV, SIGABRT, SIGFPE, SIGBUS} → `runtime_crash`；测试阶段 `timed_out` → `runtime_timeout`；测试阶段失败（退出码非 0，或退出码 0 但输出判据不满足）→ `test_fail`；
构建 / 语法检查阶段超时 → `compile_other`。OOM 被杀（rc=137、没有超时标记）按规则归 `test_fail`，与超时先后取决于机器负载（README 局限）。

### 4.13 `bench/similarity.py`


### 4.15 `bench/cli.py`

`python3 -m bench <cmd>`：`prepare` / `coverage` / `targets` / `obfuscate --level` / `verify` / `mutate --levels --max-tries` / `check-mutants --levels --oracle` / `describe --model` / `generate --model --levels --samples` / `evaluate` / `report --tag`，
以及 `e2e --backend mock` 一键跑通全链路。`generate` / `evaluate` / `report` 另有 `--task {generate,repair,all}`（默认 `all`，修复任务在 mutate 还没有产出时只给提示并跳过）。所有命令接受 `--corpus`（可多选）、`--seed`、`--jobs`、`--force`、`--workspace`、`--image` / `--cpus` / `--memory`、`--unsafe-debug`、`-v`。
退出码：0 成功；1 某阶段失败（含 evaluate / report 发现缺样本或坏行）或 e2e 断言不成立，以及未预期的运行期故障（完整堆栈追加写在工作区 `results/bench-error.log`）；
2 用法错误或缺少前置条件（缺上游产出、没有 API key、docker 不可用、spec 校验失败等）；130 被 Ctrl-C 中断（已落盘的产出可以续跑）。

`--unsafe-debug` 是唯一「放宽可信度措施」的开关：`targets` 可跳过 stub-kill、允许 mock 描述、放行没做过 stub-kill 的目标；产出不可用于正式报告，报告开头会写明。

**e2e 的验收标准**（v0.2 口径）：

- oracle 模式 100% `pass`；
- broken 模式 100% `compile_syntax`；
- wrong 模式（返回零值 / 空函数体的桩）**每个样本都不通过，且类别恰好等于 stub-kill 记录的杀死方式**：绝大多数是 `test_fail`；个别目标的桩会让后面的测试代码读到未初始化的状态而崩溃，
  归 `runtime_crash`，那是 stub-kill 已经记下的事实。v0.1 写的是「wrong 模式必须 100% test_fail」，按字面验收在有崩溃型杀死的目标上通不过；
  mock 的 wrong 回复与 stub-kill 的桩是同一份零值桩，所以类别应当逐个对得上，这也是对 attribute 与 stub-kill 两条实现路径的交叉验证
  （kill_mode 的换算与 attribute 共用崩溃信号集合，两者在这一点上不是完全独立的，信号集合本身由 `tests/test_attribute.py` 单独锁住）；
- 每个副本的 verify 与 oracle gate 全过、每个级别的每个目标都出了题（没有作废）；
- 把所有阶段再跑一遍必须全部跳过（幂等）；报告文件已生成且没有过期记录。

## 6. 可信度措施（必须实现，不可裁掉）

1. oracle gate：每个混淆副本先整体 verify；再用混淆后的原函数文本对每个目标走一遍完整 evaluate，必须 pass，不过的副本或目标作废并计数。
   gate 的结果记下检查过哪些目标（`checked_ids` / `passed_ids`）和对应的输入哈希，出题时逐个核对（6.8）。
2. stub-kill：目标函数被桩替换后项目测试必须失败，否则不入选；杀死方式逐目标记录，报告按杀死方式分层（4.5）。
3. MockLLM 三种模式的 e2e 自测固化在 `tests/test_e2e_mock.py`，CI 级别必须绿：`needs_docker` 标记的用例在 docker 或镜像不可用时默认跳过，
   `BENCH_REQUIRE_DOCKER=1` 改为失败，`scripts/ci.sh` 再检查「跳过数大于 0 即失败」，否则没有 docker 的机器上整组自测悄悄跳过、套件仍显示通过。
4. 描述泄漏检查：描述里不得出现项目标识符（含 L0 的真名），口径见 4.8（精确匹配 + 规范化匹配 + 词组警告 + 有记录的常见词放行）。
5. 全链路确定性：seed 固定则目标集、变换位置、prompt 完全一致，改名表在同一台宿主机（同一套系统头和 libclang）上也完全一致；LLM 调用 temperature=0 并带缓存。
   符号混淆的排除集依赖宿主机上 libclang 看到的系统头，与沙箱里 gcc:13 的并不相同，所以换机器或升级系统后同一个 seed 的改名表可能不同，
   混淆结果的输入哈希里带了宿主 libclang 环境的摘要，环境变了旧副本会被判定为过期。
6. 结果文件自带输入哈希，report 时校验：源码树、spec（只含影响构建与测试的字段）、prompt 模板、回复、oracle gate、评测代码、沙箱镜像；对不上的记录排除并列出原因（4.14）。
7. README 的「局限」一节如实写，报告里同一份：功能规格由 LLM 生成（规格歧义会抬高失败率，报告 L0 通过率作上限参考）、语料是知名小库（L0 可能已被记忆，这正是对照的意义）、只测 C、
   单函数粒度、测试强度依赖各库自带测试（stub-kill 只保证非空，部分目标是崩溃型杀死）、结构与语义变换覆盖的语法子集有限、L1 / L2 / L3 共用同一批回复、
   OOM 与超时的归因随负载抖动、改名表依赖宿主机的系统头。
8. 用的时候再验一遍：出题（`plan_tasks`）时重新核对 oracle gate 对应的目标集 / 副本，功能规格的输入哈希、泄漏检查器配置和重新检查的结果，stub-kill 记录；
   对不上的任务作废并按原因计数（`copy_invalid` / `no_description` / `describe_failed` / `describe_mock` / `describe_stale` / `describe_leak` / `stub_unchecked` /
   `oracle_failed` / `oracle_unchecked` / `name_not_renamed` / `not_relocated`），gate 对着另一份目标集或副本跑的直接报错并提示先运行 verify。
   不能因为中间某个阶段被跳过或重跑，就悄悄用上过期的上游产出。
9. 硬性约束：提示词禁止的东西（禁用函数、联网、汇编、定义宏）以及会绕过判据的写法（构造函数属性、`#undef` / `#pragma`）由 `postprocess` 强制，违反的候选不进沙箱、归 `policy_violation`（4.10）；
   每个语料的通过判据要求出现完成标志，提前 `exit(0)` 过不了（3.1）。
10. 不静默丢样本：生成调用失败的样本单独落盘；evaluate 写完整性记录；报告把缺口、结果文件的坏行标出来，命令返回非零；401 / 402 / 403 这类整批必然失败的错误直接中止阶段。

## 9. 实验计划（v1）

目标集：每语料 ≤ 50 个函数，预计 150–300 个；级别 4；模型 `deepseek-flash`（必跑，关闭思考，temperature 0）、`deepseek-v4-pro` 及思考版本（预算允许）；pass@1。
L1 / L2 / L3 的提示词逐字相同、共用缓存，所以每个模型真实请求数约为任务数的一半（`generate --dry-run` 先估算）；估算调用 ≤ 2400 次，输入每次 ≤ 3k token。
先用 MockLLM 把链路跑绿，再用真实 API 跑 1 个语料做试点，确认归因分布合理后跑全量。

## 10. 实现偏差记录

v0.1 之后评审确认的偏差。「处理」一列：改文档 = 现行做法更合理，已回写正文；改代码 = 契约更合理，代码已改回；两者 = 契约和代码都调整了。

| # | 主题 | v0.1 的说法 | 现状（v0.2） | 处理 / 原因 |
|---|---|---|---|---|
| 1 | 沙箱命令 | `bash -c "timeout -s KILL <t> <cmd>"`；rc=137 记超时 | `timeout` 包 `bash -c '<cmd>'`；另加 `--memory-swap`、`--ulimit core=0`、`--name`；rc=137 只有耗时不少于 timeout 才记超时（4.2） | 改文档。复合语句要整条罩住；OOM 不能误判成超时；孤儿容器要能按名字强杀 |
| 2 | 图 | matplotlib 存 PNG | 标准库直接生成 SVG（4.14） | 改文档。不新增依赖，断网也能打开 |
| 3 | 相似度 | 字符级 difflib，标识符全换成 ID | token 级，C 关键字保留，每边最多 6000 个 token（4.13） | 改文档。字符级在 200 字符以上触发 autojunk 使比值失真 |

| 5 | spec 字段 | 13 个字段，coverage 含 `gcda_glob` | 增 `vendored`、`keep_names`、`exclude_targets`、`allow_words`；删 `gcda_glob`；`digest` 不含 `url` / `license` / `notes` / `allow_words`（3.1） | 两者。`gcda_glob` 没有任何代码读它，写了不生效；notes 改一句不该让整套产出作废 |
